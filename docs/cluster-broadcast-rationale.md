# 集群广播模式：代价与取舍

> 本文说明本 broker 为什么选择「每个节点消费全量消息、再本地匹配路由」这种广播式集群，
> 而不是让节点之间同步元数据。核心结论是：
>
> **集群的稳态开销和故障恢复代价是两个独立的维度。广播模式在稳态上确实更贵，
> 但它把「需要修复的共享状态」压到了零 —— 而故障恢复的复杂度，只取决于后者。**

---

## 一、先说清楚它贵在哪

不做辩解。广播模式的代价是明确的、可量化的：

| 代价 | 具体表现 |
|---|---|
| **全量消费** | 一条消息被所有节点各消费一遍。集群 N 个节点，总线上的总读取量就是消息量的 N 倍 |
| **N 倍匹配** | 每个节点都要拿这条消息去自己的路由表里匹配一次，而实际只有 E 个节点有订阅者（E ≤ N） |
| **N 倍出站** | 发送方要写一份能被所有节点读到的东西，而不是只发给「有事做的」那几个节点 |
| **无效唤醒** | 没有订阅者的节点同样被唤醒、同样走一遍匹配逻辑，然后丢弃 |

用一句话概括：**它把「谁有事做」这个判断从发送方推迟到了每个接收方**，
于是每个接收方都要先付出一次代价，才能知道自己其实没事做。

这里有两个可以拿来判断的指标：

- **N**：节点总数。
- **E**：单条消息的平均命中节点数（即有多少个节点上真的存在匹配的订阅者）。

当 `E / N` 接近 1 时，广播几乎没有浪费 —— 反正每个节点都要处理。
当 `E / N` 远小于 1 时，广播的浪费就与 `N / E` 成正比。

**降低浪费的手段**（本文档不展开，属另一条路线）：把明显的上行流量从广播链路上摘出去，
只发给下游消费方，让扇出从 N 倍降到 1 倍。这是一个纯粹的优化，不影响本文的结论 ——
它只改变稳态开销，不改变下一节要讨论的恢复特性。

---

## 二、恢复快的根因：没有需要修复的共享状态

这是本文最重要的一句话：

> **故障恢复的复杂度，不取决于稳态开销，而取决于「有多少状态是多个节点共识出来的」。**

广播模式下，每个节点的状态是**一份只读的本地视图**：

```
节点状态 = 本机连接的客户端  +  这些客户端的订阅关系
```

这两样东西都**只属于这个节点**：订阅表不复制、不共享，连接对象本来就只存在于本进程内。
于是它有一个关键性质：

**节点宕机时，它的状态随进程一起消失，不留下任何需要清理、需要协调、需要修复的残留。**

集群层面根本不存在「节点的状态」这样一个概念 —— 因为没有任何状态是跨节点共有的。
恢复一个节点就是「把进程拉起来」（如果需要的话），而不是「把它重新纳入一个一致性协议」。

对照另一种路线（节点间复制元数据、用共识算法保证一致）：
那种设计里有一份**全体成员都要达成一致的集群状态**，每个节点都保存一份副本。
好处是查询可以直接在本地完成；代价是这份状态一旦因为故障而不一致，
就需要走选举、日志追赶、成员变更这一整套流程来修复。

下面按具体故障场景对比。为便于阅读，把前者记为**广播**，后者记为**复制**。

---

## 三、故障场景对比

### 场景 1：单个节点宕机

**广播**：该节点上的连接全部断开，客户端按 MQTT 的重连语义连到任意其他节点。
其他节点**完全无感** —— 它们的本地状态里根本没有这个节点，没有任何东西需要更新。

**复制**：必须确认这个节点是否真的下线，而不是只是变慢。
若它是共识组的 leader，选举期间提交会阻塞；若它只是 follower，
其他成员要处理「它可能带着一些未确认的状态回来」这件事。
**恢复时间取决于选举与日志追赶，而不是取决于它多快能重启。**

### 场景 2：网络分区 / 网络抖动

这是两类设计差距最大的场景。

**广播**：节点之间本来就不需要达成一致，所以分区在语义上**不构成故障**。
每个节点继续处理自己能处理的事：本节点客户端的连接、发布、订阅都在本地完成，
消息进总线，各节点按自己的消费进度读取。
分区恢复后消费进度自动接上。最坏情况是分区期间某一侧的消息出现重复或一段丢失窗口，
而这是需要靠总线语义（分区键、偏移量提交）去界定的问题，不是靠「修复集群」去解决的。

**复制**：多数派一侧可以继续，少数派一侧必须停止服务；
分区恢复后两侧的日志可能已经分叉，需要按共识规则截断其中一侧 ——
**也就是丢弃少数派上已经确认给客户端的那部分写入**。
这一步不是「恢复」，而是「有损回退」，而且它在客户端视角上是不可见的。
极端情况下（长期分区、成员反复失联）会退化成需要人工介入，
**把某个节点的数据清空、让它以全新成员身份重新加入** —— 这正是「抹掉集群重建」的来源。

### 场景 3：滚动重启与扩容

**广播**：新节点启动即用（从偏移量策略决定从哪开始消费），不需要参与任何共识过程；
旧节点退出对别人没有任何影响。**扩缩容是一系列局部事件。**

**复制**：成员变更本身是一次共识操作。每一次扩缩容，集群都会进入一段
「成员列表正在变更」的脆弱窗口 —— 而运维现实是最容易出问题的时刻，
恰好就是你动它的时候。

### 场景 4：高连接量节点的异常退出

这是最尖锐的一个场景，也是本项目最关心的场景。

假设单节点 20 万连接，每个客户端若干订阅，该节点主题树上的订阅量在百万量级。
节点异常退出时，这些连接全部重置，客户端会立刻发起重连。

**广播**：这些订阅从来就不是集群状态的一部分，所以它们的消失只是一次
「本地内存被回收」。20 万客户端重连会被分散到其余节点上，每个节点处理
自己新接入的那部分 —— **负载按客户端重连的自然节奏摊开**。

**复制**：那百万级订阅是集群状态的一部分。节点退出会让全体成员都要处理
「这份状态少了一个持有者」，而这正好发生在集群最忙的时刻（大量连接重建）。
更麻烦的是，如果这台节点随后又被判定为「只是慢、还没死」，
它会带着一份过期的状态回到集群里，需要再做一次状态协商才能重新参与。
**故障的处理过程本身变成了下一轮故障的输入。**

## 四、这条路线的前提与边界

广播模式不是免费的午餐，它成立需要三个前提，缺一个就会出问题：

1. **订阅关系不复制。** 一旦订阅表被同步到其他节点，本文开头说的
   「没有共享状态」就不成立了 —— 恢复代价会立刻回到复制路线那一侧，
   而稳态开销还是广播那一侧，两头都占。
2. **消息总线要提供「每节点独立消费」的语义。**
   用消息队列做广播，靠的是**每个节点使用各自独立的消费组** ——
   相同消费组是组内分摊（队列语义），不同消费组才是广播。
   这一点在配置上很容易写错，而写错的表现是「消息只被某一个节点收到」，
   在集群规模小的时候甚至不容易发现。
3. **顺序与幂等要有明确的落点。** 广播本身不保证任何顺序；
   顺序需要靠「按消息主题分区」来提供 —— 同一主题的消息落在同一个分区，
   各分区内部有序。跨分区不保证顺序，这是设计约束而不是缺陷。

另外两个必须接受的边界：

- **稳态带宽随 N 线性增长。** 节点数不能无限加，需要按 `E / N` 判断何时该换路线。
- **消费延迟决定了跨节点投递的延迟。** 这是广播模式相对点对点转发多出来的一段延迟，
  属于本质开销。

## 五、决策表

| 维度 | 广播（本实现） | 复制元数据（共识式） |
|---|---|---|
| 稳态带宽 | 随 N 线性增长 ← **劣** | 与订阅变更次数相关 |
| 单节点本地匹配 | 每个节点都做一次 ← **劣** | 只查本地那份状态 |
| 扩容/缩容 | 局部事件，无脆弱窗口 | 成员变更是一次共识操作 |
| 单节点宕机 | 无感，不需要任何人做任何事 | 需要选举 / 日志追赶 |
| 网络分区 | 语义上不算故障，恢复后自动接上 | 少数派停服，恢复后可能需截断日志 |
| **是否需要「抹掉重建」** | **不存在这个概念** | 极端情况需要，且对客户端不可见 |
| 故障恢复的输入 | 只是本地内存回收 | 本地状态回收 **+ 一致性协议流程** |
| 适用条件 | `E / N` 较高，或更看重可用性 | 查询必须在本地完成，且能承受共识成本 |

---

## 六、一句话总结

广播模式用**稳态的确定性开销**，换掉了**故障恢复期的不确定性**。

稳态开销是可预测的、可以按节点数算出来的、可以在压力测试里复现的；
而一致性协议在故障期的行为依赖时序、依赖网络、依赖「成员到底算死了还是算慢着」，
它不可预测，而且**它出问题的时候，恰恰是整套系统最忙、最不能出问题的时候**。

对一个要承载数十万设备连接、且运维人力有限的系统来说，
「稳态多花一点带宽」和「故障时可能需要人工介入把集群重建一次」，
前者的代价是可接受的，后者不是。

## 八、广播范围是可配置的：不是所有场景都需要广播

前面几节论证的是「**当需要跨节点投递时**，广播优于复制元数据」。但还有一个更前面的问题值得单独问：

> 这个场景下，到底需不需要跨节点投递？

MQTT 在很多业务里是**设备端与服务端之间**的通信。设备端与其他端（App 端、其他设备）之间如果走 P2P 信令，就有成本更低、时效更好的通道 —— 那么让每个节点消费全量消息就纯属浪费：没有第二个节点需要这条消息。

于是广播的范围做成三个形态：

| `broadcast-enabled` | `broadcast-filters` | 效果 |
|---|---|---|
| `true`（默认） | 空 | 全部主题都广播 —— 既有语义 |
| `true` | 非空 | 只有命中白名单的主题跨节点 |
| `false` | 忽略 | 不广播：只本节点投递 + 走数据面上行 |

中间那一行是混合场景的落点。例如设备上报的遥测只给服务端（走数据面），而端与端之间的信令需要跨节点：

```yaml
broadcast-enabled: true
broadcast-filters:
  - app/+/cmd
  - device/+/signal
```

### 两个必须守住的边界

**1. 关闭广播时，数据面上行必须照常。** 这是「省成本」与「丢数据」的分界线。上行出口是独立链路，与消息面互不影响。

**2. 连接接管通道必须照常。** 接管承载的是「同一 clientId 的旧连接该释放了」，属于会话正确性的一部分，与「跨节点 pub/sub 要不要做」是两个问题。一旦被这个开关误伤，表现为同一 clientId 在两个节点同时在线，而业务侧看到的是「指令被处理了两次」这种极难定位的现象。实现上它是独立的方法，不经过出站分流。

### 「关闭广播」与「配置漏了」必须是两个状态

所以关闭用独立开关表达，而**不能**复用「过滤器为空」—— 后者的语义是「全部广播」。反过来，过滤器全部非法时**退化为全部广播**而不是全部拒绝：配置写错应当倒向安全的一侧。

### 这个开关唯一的风险点，以及它为什么可以被验证

关闭（或收敛）广播之后，若某个主题过滤器在**多个节点**上都有订阅者，那些订阅者将永远收不到消息 —— **没有报错、没有日志、发布方与订阅方都感觉不到异常**。

这正是控制台能回答的问题。每个节点的过滤器视图都在 Redis 上（见 [管理面设计](admin-console.md)），把它们对起来看，重叠就是「需要跨节点投递」的证据：

```
GET /api/topics/overlap
```

于是「关广播」从一个凭信心的决定，变成一个**可以被验证**的决定 —— 这是把管理面数据落到共享存储之后的第一个实际收益。
