# 外挂 Redis 存 Session：能解决什么，不能解决什么

> 评估时间：2026-09-11
> 背景：Kafka 广播集群方案的内生缺陷之一是「无跨节点会话恢复」。本文评估用外挂 Redis 补这一环的可行性边界。
> 前置：`cluster-design-kafka-broadcast-assessment.md`

---

## 一、结论先说

**可以，但必须先把「会话状态」和「消息」严格分开——Redis 只能解决前者。**

如果 Redis 里既放 session 又放消息，你会得到一个**比 Raft 和 gRPC 广播都差的架构**：一个中心化的 Redis 承载全部消息流，它同时成为 SPOF 和吞吐热点。

---

## 二、必须先区分两个不同的东西

| | 会话元数据（Session） | 消息（Message） |
|---|---|---|
| 内容 | clientId、订阅关系、session_expiry、will、创建时间 | QoS 1/2 in-flight、离线消息队列 |
| 数据量 | 1M 会话 × ~1KB ≈ **1 GB** | 取决于积压深度 |
| 变更频率 | **低**：设备连上后订阅通常不变 | **等于消息率** |
| 能否放 Redis | ✅ 非常适合 | ❌ 只有高频写入一条路 |
| 该放哪 | Redis（key 带 TTL） | Kafka / 外部存储 |

**关键区别在「变更频率」**：

- 会话元数据的写入次数 ≈ 连接数 × 会话生命周期内的变更次数，是**低频**的
- in-flight 消息的写入次数 ≈ **消息率**，是高频的

在 1M 连接、30 秒上报的场景下，前者大概是每秒几百次，后者是 33k/s 起。差两个数量级。**把后者放进 Redis，就等于把消息投递路径接到中心化存储上**——这正是 MQTT broker 用 Redis 存状态最常见的性能陷阱。

---

## 二·补、订阅放每个 broker 本地、session 放 Redis：这是两层，不是二选一

澄清后的分工是自洽的，关键在于区分「运行时结构」和「持久化副本」：

| 层 | 存在形式 | 范围 | 作用 |
|---|---|---|---|
| **运行时** | 本机内存 Trie + relations | **只装本节点客户端的订阅** | 路由匹配、投递 |
| **持久层** | Redis | 会话全量（含订阅） | 崩溃恢复、客户端接管 |

**这不等于「订阅表复制到所有节点」。** 恢复时只把会话加载到**客户端实际连接的那一个** broker 的本地 Trie，不是全集群。

状态总量的差别很大：

- 共识式复制：每个节点都持有 **全集群** 的订阅表 → 内存 × N
- 你这个方案：每份会话只在**所属 broker** 的内存里 → 内存 × 1，Redis 里再加一份持久副本

所以「订阅放本地」这个核心优点**保住了**，Redis 只是给它加了一层可恢复性，没有改变路由的本地化本质。

### ⚠️ 必须避开的协议陷阱：`session_present` 与订阅必须一致

MQTT 规范里，**订阅关系本身就是 session state 的组成部分**。服务端侧的 session state 包括：

1. 会话是否存在
2. **客户端的全部订阅**
3. 已发送但未确认的消息
4. 待发送的消息
5. 已接收但未确认的 QoS 2 消息

所以只有两种自洽的选择：

| Redis 里是否含订阅 | 能返回的 `session_present` | 结果 |
|---|---|---|
| **含** | `true` | 订阅完整恢复到本地 Trie，客户端无需重订阅 |
| 不含 | `false` | 客户端重新 SUBSCRIBE，broker 重建本地路由 |

**中间态是协议不允许的**：返回 `session_present = true` 但订阅没恢复，会让客户端以为还订阅着，而 broker 里没有任何路由 —— **静默丢消息，且客户端无法察觉**。这是最难排查的一类故障，因为它不报错、不断连，只是消息不再到达。

**结论：既然要用 Redis 做会话恢复，Redis 里就必须包含订阅关系。** 想省掉订阅的存储，就只能退回 `session_present = false`，那就等于放弃了会话恢复的意义（客户端还是要重订阅，Redis 只剩下"记住会话存在"这点作用）。

> 与 §五 的关系：那一节论证的是「为省一轮 SUBSCRIBE 而引入 Redis 是否值得」。一旦决定引入，本节就是硬约束——**Redis 必须装订阅**，没有折中方案。

### 随之而来的问题：客户端接管（Takeover）

客户端从 broker A 重连到 broker B，B 从 Redis 恢复订阅并写入本地 Trie。但如果 **A 还活着、仍持有这些订阅**，就会出现双份路由 → **重复投递**。

而订阅表不复制的话，B 根本不知道 A 手里有这些订阅。

解法很自然：**在同一个 Redis 会话记录里顺便存 owner node**，B 加载时读到旧 owner 是 A，就直接定向通知 A 释放该客户端的订阅。

这带来一个顺带的好处：`owner node` 字段本身就是一份 **clientId → node 目录**，前面提到的「定向投递只能靠广播实现」的缺口自动补上了。

**但必须守住一条铁律：`owner node` 只在重连 / 接管这类低频路径上读，绝不进消息投递路径。** 把 Redis 读放进投递路径，就退化成「每次发布都读一次外部存储」的形态。

### 三个路径的读写频次对照

| 路径 | 频次 | 是否读/写 Redis |
|---|---|---|
| 消息投递（pub/sub 匹配） | 高频（= 消息率） | ❌ **绝不** |
| 订阅变更 / 会话属性变更 | 低频 | ✅ 写 |
| 连接建立 / 重连 / 接管 | 中低频 | ✅ 读 |

---

## 三、只能解决一半，另一半要靠别的

### ✅ 能解决：会话元数据 + 订阅关系的跨节点恢复

节点宕机后，客户端重连到其他节点，从 Redis 取回会话 → `session_present = true`，不需要重新订阅。

### ❌ 不能解决：in-flight 消息与离线消息

除非接受「每条消息一次 Redis 写」。这会：

- 把 Redis 变成消息投递路径上的必经节点（延迟 + 吞吐双杀）
- 在 1M 连接下需要 Redis Cluster，且写入量线性随消息率增长
- 与 Kafka 方案叠加后形成**两个中心化依赖**

**所以：in-flight 与离线消息的持久化应该走 Kafka（或专门的消息存储），不要走 Redis。**

---

## 四、必须用 write-back 模式，不能把运行时状态放 Redis

这是设计上最容易犯的错。反例很典型：把 session 当成 Redis 里的记录，**每次消息投递都去 `GET` 一次 session** —— 这会让每一次消息投递都变成一次网络往返。

正确做法是三层：

```
客户端连接 → 从 Redis 加载会话 → 放入本机内存
运行时      → 读写全在本机内存（零网络）
状态变更    → 异步 / 批量回写 Redis
节点宕机    → 新节点从 Redis 恢复
```

即 **write-back cache**：Redis 是「冷启动和故障恢复的加载源」，不是「运行时状态的真源」。

### 但这里有个必须承认的缺口

write-back 有回写窗口。而**节点宕机是非优雅退出，不会触发「断连时保存」**。

所以：

| 状态 | 回写时机 | 宕机时会丢什么 |
|---|---|---|
| 订阅关系 | 变更时同步写 | 几乎不丢（变更本身就是触发点） |
| 会话属性 | 变更时同步写 | 几乎不丢 |
| in-flight 消息 | 只能异步批量 | **丢最近一批** |

**结论：write-back 模式让「会话元数据」基本可靠，但「消息」仍然有窗口。** 这不是实现问题，是 write-back 的固有性质。

## 五、一个反直觉的判断：在你的架构下，会话恢复的价值被高估了

这一点值得单独说，因为它直接影响要不要引入 Redis。

**在「订阅本地化 + Kafka 扇出」的架构里，客户端重新订阅的成本几乎是零。**

对比一下「不恢复会话」的代价：

| 需要重新做的事 | 成本 |
|---|---|
| 客户端重新发 SUBSCRIBE | 一次下行 + 一次上行（本来重连也要走） |
| broker 重建订阅关系 | **本地 Trie 写入，零网络、零共识** |

因为在你的方案里订阅表**本来就不复制**——每个 broker 只管自己的路由，重新订阅就是一次本地内存写入。这跟共识式方案完全相反：共识方案里重新订阅要过一遍 Raft 提案（这才是灾难）。

所以：

> **丢会话元数据的真实代价，只是「客户端要多发一轮 SUBSCRIBE」，而不是「集群要承担一轮写风暴」。**

真正丢不掉的是**消息**：QoS 1/2 的 in-flight 和离线消息。而消息的归宿本来就是 Kafka/外部存储，不是 Redis。

**所以更合理的分工是**：

- **不为「会话恢复」引入 Redis** —— 收益小（省一轮 SUBSCRIBE），成本高（多一个中心化依赖）
- **为「消息不丢」把持久化做好** —— 这才是真正的痛点，而它走 Kafka 链路，不需要新增组件

### 什么情况下会话恢复才真的值钱

取决于你的 QoS 分布：

- **设备侧大量用 QoS 0**（IoT 遥测的常态）→ 没有 in-flight，没有离线消息，会话恢复**几乎没有价值**
- **下行命令用 QoS 1 且要求必达** → in-flight 有价值，但那是消息持久化问题，不是会话元数据问题
- **用了 MQTT 5 且订阅关系复杂**（几十上百个 filter）→ 重新订阅才有点成本，但仍是本地写入

## 六、如果确定要引入 Redis，设计要点

### 6.1 键设计

```
session:{clientId}          → Hash
                              ├─ subscriptions   [topic_filter + qos + opts]   ← 必须含，否则只能返回 session_present=false
                              ├─ owner_node      归属 broker id                 ← 用于接管 + 定向
                              ├─ session_expiry / clean_session
                              ├─ will            遗嘱消息
                              └─ created_at / version
                              TTL = session_expiry，让 Redis 自己清理
retain:{topic}              → 保留消息（如果要，见 6.6）
```

**一个会话用一个 Hash 装完**，加载时一次 `HGETALL` 取全，避免多次往返。

`clientId` 做 hash tag（`{clientId}`）可以保证同一会话的多个 key 落在同一 slot，方便用 Lua 做原子操作——**接管的「读 owner + 改 owner」必须原子，否则两个 broker 同时接管会双双认为自己是 owner**。

**必须用 Redis 的 TTL 机制对齐 MQTT 的 session_expiry** —— 这是 Redis 相比自建存储的最大优势：过期清理不占你的代码和 CPU。注意 `will` 消息的 TTL 语义与 session 不同（遗嘱在异常断连时触发），如果依赖 TTL 过期来触发遗嘱，需要单独设计。

### 6.2 容量与吞吐估算（1M 连接）

| 项目 | 估算 | 结论 |
|---|---|---|
| 会话元数据内存 | 1M × ~1KB = **1 GB** | 单节点内存可容纳 |
| 连接时读取 | 1M 次 HGETALL，摊在重连窗口内。若集中在 10 分钟内 → 1.7k/s | 轻松 |
| 订阅变更写入 | 低频（几百/s 量级） | 轻松 |
| **in-flight 写入** | **= 消息率，33k/s 起，f=1/5 时 200k/s** | **需要 Redis Cluster，且不该做** |

结论：**只放会话元数据的话，Redis 的负载很轻；一旦开始放消息，负载立刻上两个数量级。**

### 6.3 部署形态

- 用 **Redis Cluster**（3 主 3 从起步），不要单实例 —— 1M 连接的场景下 Redis 不可用是全局故障
- 与 Kafka 同 DC，**不跨 DC 复制**（与「禁止跨区数据同步」原则一致；跨 DC 的场景下每个 DC 各自一套）
- 监控重点：内存水位、`HGETALL` 的 P99、连接数

### 6.4 必须明确定义「Redis 不可用」时的降级行为

这是设计里最容易被漏掉、但故障时最致命的一条。两种选择：

| 降级策略 | 行为 | 适用 |
|---|---|---|
| **降级为新会话** | 连接受理，session_present=false，客户端重新订阅 | ✅ 推荐：**可用性优先**。IoT 设备通常能接受重新订阅 |
| 拒绝连接 | 返回 ServerUnavailable | ❌ 不推荐：Redis 故障直接变成接入故障，扩大爆炸半径 |

**推荐第一种。** 理由是：会话元数据丢失的代价（一轮 SUBSCRIBE）远小于拒绝接入的代价（设备全部掉线）。

### 6.5 幂等与去重

节点宕机后从 Redis 恢复可能产生重复（write-back 窗口内的重复回写、恢复时的并发）。需要：

- 会话带版本号或时间戳，恢复时按新者胜
- 应用层对重复投递做去重（这一条本来就要做，见前文档的弱一致问题）

## 七、引入 Redis 后，方案的完整图景与代价重算

| 组件 | 承载 | 失效影响 |
|---|---|---|
| MQTT broker | 接入、本地路由、本地投递 | 单节点故障 → 其客户端重连 |
| Kafka | 跨节点消息扇出 | 跨节点投递全断，本地仍正常 |
| **Redis** | 会话元数据 | 降级为新会话，接入不受影响 |

**要诚实看待的一件事：引入 Redis 后，「无复制状态」这个最大的优点部分丧失了。**

你重新引入了一个共享状态存储。虽然它比共识式方案好得多（写 1 次而不是 N 次、不需要 quorum、没有 leader），但「共享状态带来的耦合」回来了。

### 与共识式方案的对比需要重新算

| | 共识式（状态复制到每节点） | 你的方案 + Redis |
|---|---|---|
| 状态写入 | 提案 → N 次复制 + 多数派确认 | **1 次 Redis 写** |
| 状态读取 | **本地内存，零网络** | 连接时 1 次网络读（运行时在内存） |
| 写放大 | N 倍 + 共识开销 | 1 倍 ✅ |
| 读延迟 | 零 ✅ | 重连时 +1 次 RTT |
| quorum 风险 | 有 | **无** ✅ |
| 故障后状态 | 僵尸污染，需人工清理 | 干净，TTL 自动过期 ✅ |
| 新增依赖 | 无 | Kafka + Redis 两个 |

**本质是用「写放大 + quorum 风险」换「读延迟 + 两个中心化依赖」。** 在重连频繁、订阅变更频繁的场景下这笔交易明显划算；在状态读取极高频的场景下不划算——而后者恰恰是「把消息也放进 Redis」才会出现的情况。

## 八、建议的完整分工

```
设备 ──MQTT──> broker ──┬── 本地路由 + 本地投递（内存 Trie）
                        ├── 上行数据 ──> Kafka ──> 云端业务/数仓   ← 数据面
                        └── 跨节点投递 ──> Kafka（广播 topic）      ← 控制面/消息面

broker ── 会话元数据 ──> Redis（key 带 TTL，write-back 回写）        ← 会话面
```

三条链路各司其职：

1. **数据面**：上行数据走 Kafka 出口，**不经过 MQTT 集群广播**（前一文档已论证，扇出从 N 倍降到 1 倍）
2. **消息面**：跨节点的 pub/sub 走 Kafka 广播 topic（每节点独立 group）
3. **会话面**：Redis 放**会话（含订阅关系与 owner node）**，不放消息；write-back 模式；Redis 不可用时降级为新会话

**Redis 里唯一不该出现的东西，就是消息本身。**

### 三层的状态归属

| 数据 | 归属 | 是否复制 |
|---|---|---|
| 运行时路由（Trie / relations） | 每个 broker 本地内存 | **不复制**（只装本节点客户端的订阅） |
| 会话持久副本（含订阅、owner） | Redis | 单份，非全节点复制 |
| 上行数据 | Kafka → 云端 | 不经过集群 |
| 跨节点 pub/sub 消息 | Kafka 广播 topic | 每节点独立 group |
| in-flight / 离线消息 | Kafka 或专用存储 | **不进 Redis** |

## 附：需要确认的决策点

| # | 问题 | 影响 |
|---|---|---|
| 1 | 设备侧 QoS 分布是什么？QoS 0 占比多少？ | QoS 0 占比高 → 会话恢复价值很低，可能不需要 Redis |
| 2 | Redis 里是否包含订阅关系？ | **必须含**，否则只能返回 `session_present=false`（协议约束） |
| 3 | 是否存 owner node？接管如何做？ | 不存 → A/B 双份路由重复投递；存 → 「读 owner + 改 owner」必须用 Lua 保证原子 |
| 4 | in-flight / 离线消息的持久化走哪条链路？ | 不能走 Redis，需明确走 Kafka 还是专用存储 |
| 5 | session_expiry 业务上定多长？ | 决定 Redis 内存水位与 TTL 策略 |
| 6 | Redis 不可用时是降级还是拒绝？ | 建议降级为新会话，可用性优先 |
| 7 | 是否真的需要跨节点会话恢复？ | 本方案下重新订阅是本地操作，成本极低，需评估收益是否值一个新增依赖 |
