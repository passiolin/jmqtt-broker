# 服务端数据接入：直连 Kafka，而不是 MQTT 订阅

> **结论**：平台侧消费设备数据，走 Kafka 消费组；不走 MQTT 订阅，也不走 MQTT 共享订阅。
>
> Broker 的定位是**边缘协议适配器** —— MQTT 进、Kafka 出。设备侧只认 MQTT，
> 平台侧只认 Kafka，中间不做第二套消费语义。
>
> 本文说明为什么「用 MQTT SDK 订阅来消费数据」在数据量大时会丢，以及 Kafka 直连
> 补上的恰好是哪几块。

---

## 一、为什么 MQTT 订阅消费在数据量大时会丢

这不是 SDK 的实现质量问题，而是 **MQTT 这个协议在「服务端消费」这个用法下的固有边界**。
下面五条都是机制层面的，逐条说清因果。

### 1. Broker 侧的发送队列是有界的，溢出即丢 —— 且丢得静默

任何一个能承载高并发的 broker 都不可能让写缓冲无限增长：一个连上就不再读 socket 的
消费者，足以把 broker 的内存吃光。所以每个连接都必须有一个**有界的发送队列**，
满了只能丢。

本实现的这道闸门就是 `max-mqueue-len`（超限丢弃最旧的），代码注释里写得很直白：
「这是 QoS 1/2 投递保证的实际破损点」。

**关键点：QoS 1 完全不解决这个问题。**
QoS 1 保证的是「已进入 in-flight 的消息在连接断开后会被重发」；
而慢消费者场景下，消息是在**入队之前**就被丢弃的 —— 客户端根本不知道曾经有过这条消息，
broker 也不会为此重传。**这不是重传能覆盖的丢失窗口。**

### 2. In-flight 窗口封顶单连接吞吐

未确认的 QoS 1/2 达到 `max-inflight` 就停止下发，等确认。这是规范要求的流控，
但它意味着一件事：

```
单连接吞吐 ≈ in-flight 窗口 / 往返时延
```

窗口是几十条的量级、跨地域 RTT 是几十毫秒量级 —— 单条 MQTT 连接能扛的吞吐是有限的，
而**它不随你加 CPU 而增长**。要提吞吐只能加连接数。

### 3. 没有背压传播

MQTT 里没有任何机制能让消费者告诉发布者「我跟不上了」。
发布者是设备，设备不会因为平台侧慢就少发一条数据。

于是过载是**必然发生**的，而且：

- broker 不会拒绝（拒绝设备等于让设备掉线，代价更大）
- 也没有地方把压力存下来（只能在内存里排队，然后丢）
- **整个过程是静默的** —— 丢的是队列头部的消息，没人收到「你丢了一条」的信号

### 4. 没有位点，就没有重放

这是最根本的一条。MQTT **没有「消费进度」这个概念**。

- 消费者重启 → 除非有持久会话 + 离线队列，否则期间的消息永久消失
- 消费者发版 / 扩缩容 → 同样
- 写错了逻辑要回补 → 无法重放，数据就是没了

而且即使有持久会话，离线队列本身也是有界的、也是丢最旧的（`max-offline-queue-len`）。
**它是一层缓存，不是一个可重放的数据流。**

### 5. QoS 2 也不解决问题

QoS 2 把投递变成四步握手（PUBLISH → PUBREC → PUBREL → PUBCOMP），
代价是单连接吞吐再降一个量级；而 in-flight 窗口照样封顶、位点照样不存在。
**它提升的是「不重复」，不是「不丢失」。**

### 6. 那么共享订阅呢？—— 它只加了「分摊」，上面五条一条都没解决

共享订阅（`$share/{group}/{filter}`）做的是：把匹配同一个过滤器的消息
**分摊**给组内的多个消费者。

它确实解决了「一个消费者扛不住」中的一个维度 —— 但每个消费者背上仍然是：
同样有界的连接、同样封顶的窗口、同样没有的背压、同样不存在的位点。
而且：

- 分区与再均衡是 **broker 自己实现的**，语义、可观测性、稳定性都弱于 Kafka 的分区分配协议
- 消费者在什么粒度上分摊、分摊过程中消息会不会乱序或丢失，取决于实现细节而非协议保证
- 没有任何指标能告诉你「这个消费者组落后了多少」—— 因为「落后多少」这个概念在 MQTT 里不存在

**共享订阅真正合适的场景是：消费者本身也是 MQTT 参与者。**
比如两个边缘节点共担一批设备的接入、一个轻量工具需要按组分摊。
它的服务对象是 MQTT 世界内部的水平扩展，**不是平台侧的数据管道**。

## 二、Kafka 直连补上的正好是那几块

| 上面的问题 | MQTT 订阅 | Kafka 消费组 |
|---|---|---|
| **溢出** | 内存有界，丢最旧且**静默** | 消费者慢就慢，数据留在磁盘上（retention 内），不丢 |
| **背压** | 无传播机制，过载必然静默发生 | **拉模型**：消费者自己控制节奏；`lag` 是一等公民指标 |
| **位点** | 不存在 | 偏移量提交；重启 / 发版 / 扩容都从位点续读 |
| **重放** | 无法重放 | 可重置 offset 重读（回补、修逻辑、接新下游） |
| **扩容** | 每消费者一条连接，分摊语义由 broker 自定义 | 分区分配是协议的一部分，扩容 = 加消费者 |
| **顺序** | 跨消费者无顺序保证 | 分区内有序，**键决定顺序边界** |
| **下游复用** | 一份数据一个消费者，很难同时喂多个系统 | 同一条流可被数仓 / Flink / 告警以不同 `group.id` 各自消费 |

一句话概括这一节：

> **共享订阅想解决的问题（组内分摊），Kafka 消费组的语义就是「相同 group.id」——
> 而且顺带把位点、重放、背压三样一起给了。**

所以服务端根本不需要 MQTT 共享订阅；需要的是**别用 MQTT 消费**。

## 三、落到本 broker：数据面（uplink）

Broker 在这里的角色是**协议适配器**：把 MQTT 的发布流按过滤规则写进一个 Kafka topic，
之后平台侧就是普通的 Kafka 消费者。

```yaml
jmqtt:
  broker:
    kafka:
      enabled: true
      bootstrap-servers: kafka-1:9092,kafka-2:9092
      # 服务端读的那个 topic
      uplink-topic: iot-uplink
      # 哪些主题算上行。建议显式按前缀列出, 不要依赖「全部都是上行」
      uplink-filters: ["v1/telemetry/#", "v1/event/#"]
      # 命中上行的消息是否只走数据面、不再进集群广播
      uplink-exclusive: true
      # 数据面的分区键: topic(默认) 或 device
      uplink-key: device
```

### 四个配置项各自解决什么

| 配置 | 作用 | 注意 |
|---|---|---|
| `uplink-topic` | 服务端读的 topic | 与集群总线 topic 分开，别混用 |
| `uplink-filters` | 哪些主题算上行 | 建议显式列出。用「全部」会把下行指令也写进去，污染数据管道 |
| `uplink-exclusive` | 命中上行的消息**只**进数据面，不进集群广播 | **服务端直连 Kafka 时应当打开** —— 集群里已经没有 MQTT 订阅者在等这些消息了，不打开就是白白付出 N 倍扇出 |
| `uplink-key` | 分区键 | **遥测必须用 `device`**，理由见下 |

### `uplink-key` 为什么是个关键配置

Kafka 只保证**分区内**有序，所以键的选择决定了下游能依赖哪种顺序。

- **`topic`（默认）**：键 = MQTT 主题。保证同一主题的消息有序。与集群广播一致。
- **`device`**：键 = 设备标识（`clientId`）。保证**每个设备自己的时序**有序，
  并把流量按设备散到各分区。

**遥测场景下必须用 `device`，原因不是顺序而是吞吐：**

设备遥测往往集中在少数几个主题上（典型情况是**只有一个**，比如 `v1/telemetry`，
设备身份在 payload 里）。这时按主题分区会把**全量流量压进同一个分区** ——
下游无论加多少个消费者，能并行读的只有持有那个分区的那个实例，
**这个分区就是整条数据管道的吞吐上限**，而且它是一个非常隐蔽的天花板：
你会看到消费者数量上去了、CPU 却很闲。

按设备分区则天然散开，且正好提供数据管道真正需要的顺序边界 ——
**每个设备自己的时序**，而不是跨设备的主题时序。

设备标识缺失时（例如服务端主动下发的消息没有来源客户端）自动**回退为主题**。
回退而不是发 `null` key：`null` key 会让 Kafka 在各分区之间轮转，
同一个设备的消息被散到不同分区，有序性直接消失。

### 记录格式（下游要知道的全部）

```
key      = 分区键(按 uplink-key 决定, 默认是 MQTT 主题)
value    = 原始 payload 字节, 不做任何编码包装
headers:
  jmqtt-topic      MQTT 主题
  jmqtt-client-id  来源设备标识(clientId)     ← 下游取设备身份不需要解析 payload
  jmqtt-broker-id  来源 broker 标识
  jmqtt-qos        发布 QoS
  jmqtt-retain     是否保留消息
  jmqtt-dup        是否重传
```

两点说明：

- **主题在 header 里，不再由 key 承载。** 因为数据面按设备分区时 key 不再是主题 ——
  消费端不能靠 `record.key()` 还原主题。解析时优先读 `jmqtt-topic`，
  读不到才回退到 key（兼容早期写入的数据与手工调试消息）。
- **设备标识在 header 里。** 下游做设备维度聚合、分组、去重时直接读 header，
  不必依赖 topic 结构或 payload 格式。

### 服务端侧的几条约定

```java
// 一个 group.id 代表一个「逻辑消费者」;
// 同一 group 内的分摊 —— 这正是共享订阅原本想得到的语义
props.put("group.id", "iot-telemetry-warehouse");
// 关闭自动提交: 处理完再提交, 否则「读到了但没处理完」也会推进位点
props.put("enable.auto.commit", "false");
```

1. **用 `group.id` 表达「谁」**：同一个业务系统用同一个 group（组内自动分摊），
   不同业务系统用不同 group（各自读全量）。
2. **手动提交位点**，处理完成后再提交。自动提交会在「批量拉取后、处理前」推进位点，
   进程崩溃就丢一批。
3. **业务侧幂等**：Kafka 通常按 at-least-once 使用，重复是正常的。
   按 `(设备标识, 序列号或时间戳)` 去重，比追求端到端 exactly-once 划算得多。
4. **盯 `lag`**：这是这套架构里最重要的健康指标 —— 它把「消费者跟不跟得上」
   变成了一个可以直接看、可以告警的数字。而在 MQTT 订阅模式下，这件事是没有指标可看的。

## 四、两条必须说清的边界

### 1. `uplink-exclusive=true` 之后，broker 内部的 MQTT 订阅者也收不到了

这是**互斥**的：命中上行过滤器的消息要么只进数据面，要么同时也进集群广播。

所以打开它的前提是「确认没有 MQTT 侧的消费者在等这些主题」。
如果确实存在（例如设备需要订阅自己的回显、或某个运维工具通过 MQTT 看数据），有三个选择：

- 保持 `uplink-exclusive=false`，接受 N 倍扇出（集群里没有订阅者的节点也会读到再丢弃）
- 把两类主题拆开：遥测走数据面独占，回显另行设计主题
- 让那个 MQTT 侧消费者也改成读 Kafka

**这是架构判断，不是调优参数。** 建议先用真实流量量出「一条消息平均需要投递到几个节点」
（`E` 指标）再决定。

### 2. Broker → Kafka 这一段仍然是尽力而为

「服务端直连 Kafka 就不丢」准确的表述是：**Kafka 之后不再丢**。

Broker 到 Kafka 之间还有一个**有界的出站队列**（`queue-capacity`），
满了同样会丢弃并计数 —— 因为这段队列位于 MQTT 发布路径上，
绝不能因为 Kafka 故障而阻塞设备发布（`max-block-ms` 必须设小，也是同一个道理）。

所以这一段要压风险，靠的是：

| 手段 | 说明 |
|---|---|
| Kafka 侧的高可用 | Kafka 可用时出站队列会一直有空间，这一段的丢弃就趋近于零 |
| 盯 `dropped` 指标 | `/open/api/jmqtt/info` 的 `clusterBus.dropped`。它上升说明写总线跟不上 |
| 盯 `outboxSize` | 持续接近 `queue-capacity` 说明即将开始丢弃 |

**反过来看，这恰恰也说明为什么不该用 MQTT 订阅做服务端消费**：
MQTT 订阅模式下，被丢弃的**只有** broker 内的那份内存队列，没有第二层兜底；
而走 Kafka 时，broker 只需要把消息**写入** Kafka（一个高可用、低延迟的操作），
之后的一切都是持久化存储上的事。

## 五、与 MQTT 5.0 共享订阅声明的关系

本 broker 在 CONNACK 里声明 `Shared Subscription Available = 0`，
并对 `$share/...` 明确返回原因码 `0x9E`（不支持共享订阅）。

**这不是一个待补的缺口，而是定位的结果。** 平台侧消费不经 MQTT，
所以服务端接入这条路上，共享订阅本就不该出现。

它真正的服务对象是 MQTT 世界内部的水平扩展 —— 需要分摊的 MQTT 侧消费者。
将来如果确有这种需求（例如两个边缘节点共担一批设备），再实现它也不迟：
那时它是一个**为 MQTT 消费者准备的一等功能**，而不是「服务端接入的替代品」。

顺带说明为什么现在是**明确拒绝**而不是「照常接受」：
`$share/{group}/{filter}` 语法上是一个合法的过滤器，但 `$share` 是保留前缀、不会
被当作普通主题层参与匹配。照常接受的结果是**订阅成功但永远收不到任何消息** ——
静默丢消息。宁可让客户端在订阅那一刻就知道不支持。

## 六、一句话总结

| 场景 | 用什么 | 为什么 |
|---|---|---|
| **平台侧消费设备数据（数仓、实时计算、告警）** | **Kafka 消费组** | 位点、重放、真正的背压、分区分配 —— MQTT 一样都没有 |
| 服务端要「一份数据多个业务各读一遍」 | 不同 `group.id` | 与 MQTT 共享订阅相比，还多了位点与可重放 |
| 需要分摊的 MQTT 侧消费者（边缘节点、工具） | MQTT 共享订阅（当前未实现） | 它属于 MQTT 世界内部的扩展 |
| 设备侧接入 | MQTT | 设备只认这个 |

Broker 只做一件事：**把 MQTT 的发布流按规则落到 Kafka 上**。
在这之后，消费这一侧的所有问题（位点、重放、背压、扩容、下游复用）
都交给 Kafka 解决 —— 那是它被设计出来要解决的问题，
而 MQTT 从来不是为此设计的。
