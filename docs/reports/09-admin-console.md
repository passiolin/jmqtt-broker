# 09 · 管理台与节点排水

> 时间：2026-09-12
> 目标：新建 jmqtt-admin（backend + frontend），实现设备侧可视、主题可视、可手动驱逐客户端；
> 同时把管理面的数据落到 Redis，由控制台直接读取。

## 二、核心决策

### 1. 管理面走 Redis，控制台不直连 broker

控制台要的是「整个集群的视图」，而它不在集群里。逐个 HTTP 请求各节点有两个问题：控制台必须能访问每个 broker 的管理端口（生产里通常不在同一张网）；「视图」被拆成 N 次 RPC，任何一次失败都会让页面残缺 —— 而残缺的视图比看不到更危险。

改成读 Redis 之后，「节点是否可达」由**心跳是否存在**表达，而不是由**请求是否超时**表达。后者无法区分「节点挂了」与「网络抖了一下」。

附带好处：控制台重启不影响进行中的运维动作（驱逐是 broker 在执行）。

### 2. 排水流程必须由控制台编排，且必须拆成四步

「停调度」这一步在控制台的权限范围之外 —— 可能是改 Nginx 权重、改 K8s readiness、改云负载均衡后端组，各家接口不同且通常需要另一套权限。所以流程拆成四个显式动作，每个都能单独重试与观察。

**没有做「点一下全干完」的接口**：那会把一个必须由人负责的步骤埋进自动化里，而出问题时那段自动化不会告诉任何人它跳过了什么。

### 3. 驱逐只关连接，不删会话

这是整个操作能成立的前提。被驱逐的客户端重连到另一节点后走既有的「取得归属 + 跨节点接管」路径：`sessionPresent=true`、订阅被恢复、离线积压继续投递、未确认的 QoS 1/2 以 `dup=1` 重发。

反过来，如果顺手删了会话，客户端会以为自己是全新的 —— 表现为「订阅没了、离线消息没了」，而这恰恰是驱逐本不该造成的破坏。

### 4. 分批 + 限速 + 硬上限，且都是安全阀

一次性断开十万条连接会同时触发：十万条遗嘱涌入路由与总线、十万次重连打向剩余节点、十万条会话归属转移。任一件都足以把集群从「一次运维」变成「一次故障」。

所以 `max-evict-per-task`（默认 5000）做在配置里而不是请求参数里 —— 请求只能在配置允许的范围内调整。控制台与 broker **双重校验**：控制台先拦并给出「建议比例不超过 X%」这类可执行提示，broker 再兜一次防止绕过控制台直连 Redis。

### 5. 严格串行

同一节点同一时刻只允许一个驱逐任务。两个任务并行时各自按自己的节奏断开，合起来的速率就不再是任何一方设定的值 —— 限速只有在「谁在限速」唯一时才有意义。

## 三、实现中的三个关键判断

### 1. 过滤器视图是「重算」而不是「增量计数」

增量计数（订阅 `HINCRBY +1`、退订 `-1`）开销极小，但有一个无法回避的问题：**同一件事可能被写两次**。会话从持久层恢复时会把订阅重新写回本地主题树（那批订阅其实早就在了）；节点重启后本地树是空的，而增量计数却从 Redis 上的旧值继续累加。

于是计数只会越漂越远，而且**漂移不可自愈** —— 没有任何时刻能确定「现在这个数是对的」。

改成从主题树重算后，漂移在结构上不可能发生。代价是一次遍历，用**订阅变更版本号**做闸门：版本没变直接跳过，变更后按间隔合并只算一次。

### 2. 客户端注册表必须增量，并靠三种时机对账

十万条目的全量重写是几十 MB 传输，无法按秒级频率做。所以增量 `HSET`/`HDEL`，并靠启动时、Redis 重连后、发现增量被丢弃时做全量对账。

对账是「先 `DEL` 再分块写回」。必须 DEL：只做增量补齐的话，「曾经连过但后来因故没发出 HDEL」的条目会永远留下成为**幽灵客户端**。

### 3. 命令必须自带时效，且由节点侧判断过期

命令走 Redis 列表，没有 TCP 那样的连接状态保证时效。节点离线期间下发的命令会在节点回来后执行 —— 对「驱逐」这种动作，**一小时后才执行比不执行更危险**。

超龄判断放在节点侧，因为只有节点知道「我是什么时候取到这条命令的」。控制台侧的「以为过期了就不发」解决不了队列里已经躺着的那一条。

## 四、验证

### 端到端（`tools/run-admin-drain.sh`，35 项全通过）

环境：真实 Redis + node-a(1901) + node-b(1902) + 控制台(9100) + 12 个真实 MQTT 客户端（cleanSession=false，各订阅 2 个过滤器）。

| 分组 | 关键断言 |
|---|---|
| 鉴权 | 无令牌 401；错误密码被拒；登录取得令牌 |
| 节点发现 | 2 节点 / 2 在线；node-a 连接数 = 12；Redis 可达 |
| 客户端列表 | 12 条；协议版本与心跳正确；12 个持久会话 |
| 主题列表 | 过滤器去重 13（12 独有 + 1 共用）；共用过滤器订阅者数 = 12 |
| 踢下线 | 命令命中；node-a 12→11；node-b 0→1 |
| 排水创建 | CREATED；超上限（999999）被拒 |
| 预检 | 完成且未告警（无持续新连接） |
| 阶段约束 | **未确认停调度时 start 被拒**；确认后 LB_CONFIRMED；start 后 EVICTING |
| 排水结果 | **COMPLETED**；目标节点减少 11、其他节点增加 11、节点报告断开 11 |
| 节点分布 | **node-a 归零；node-b = 12** |
| 订阅恢复 | **node-b 过滤器数 = 13**（订阅随会话恢复，客户端未重订阅） |
| 会话保留 | Redis 会话键 12 个全在 |
| 客户端侧 | **12 个客户端重连后 sessionPresent 全为 true**；全部落在 node-b |

最后两条是整个验证的核心：客户端**只在首次连接时订阅**，重连后不再订阅。node-b 出现 13 个过滤器、且 CONNACK 的 `sessionPresent` 全为 true，说明会话与订阅都被完整恢复了 —— 这正是「驱逐只关连接」这个设计要保证的事。

## 五、顺带实现的架构改进：集群广播开关

来自一条业务判断：**MQTT 很多时候是设备端与服务端之间的通信**；设备端与其他端（比如 App 端）可以通过 P2P 信令通信，有成本更低、时效更好的方案。所以很多场景下让每个节点消费全量消息纯属浪费。

于是广播变成可配置的：

| `broadcast-enabled` | `broadcast-filters` | 效果 |
|---|---|---|
| `true`（默认） | 空 | 全部主题都广播（既有语义，不改变任何现有行为） |
| `true` | 非空 | 只有命中白名单的主题跨节点 |
| `false` | 忽略 | 不广播：只本节点投递 + 走数据面上行 |

两个必须守住的边界：

1. **关闭广播时数据面上行照常** —— 否则就是把「省成本」做成了「丢数据」；
2. **连接接管通道照常** —— 它承载「同一 clientId 的旧连接该释放了」，属于会话正确性的一部分。被误伤的表现是同一 clientId 在两个节点同时在线，业务侧看是「指令被处理了两次」这种极难定位的现象。

「关闭广播」与「配置漏了」必须是两个状态：关闭用独立开关表达；过滤器全非法时**退化为全部广播**（配置写错应当倒向安全的一侧）。

**这个开关的唯一风险点**是：若某过滤器在多个节点上都有订阅者，广播关掉后那些订阅者会静默收不到消息。而控制台的 `/api/topics/overlap` 恰好能查这件事 —— 每个节点的过滤器视图都在 Redis 上，重叠就是「需要跨节点投递」的证据。于是「关广播」从一个凭信心的决定变成一个可验证的决定。

## 六、解耦数据面的分区键（前一轮遗留）

写文档时发现数据面的 record key 只能是 MQTT 主题，而**遥测主题通常高度集中**（典型只有一个，设备身份在 payload 里）。按主题分区会把全量流量压进一个分区，下游加再多消费者也只能串行读 —— 这个分区就是整条管道的吞吐上限，且是很隐蔽的天花板（消费者数量上去了、CPU 很闲）。

修法：主题改走 header（`jmqtt-topic`），新增 `uplink-key: topic|device`（默认 `topic`，不改变现有行为）。设备标识缺失时**回退为主题而不是发 null key** —— null key 会让 Kafka 在各分区轮转，同一设备的消息散开、有序性消失。

## 七、遗留

- **真实 Kafka 未验证**：广播开关的过滤器匹配与接管通道不受影响，有单测覆盖；但跨节点消息投递仍无真实 Kafka 上的端到端验证（沙箱 4GB 虚拟内存上限，Kafka 起不来）。
- **保留消息列表**未在控制台展示（节点概要里有总数）。需要时可照过滤器视图的做法发布。
- 控制台的**排水任务历史只存在进程内**，重启清空。驱逐由 broker 执行，因此不会影响进行中的动作。
- 前端**备用构建路径不支持 `<style scoped>`**（会警告并按全局样式输出）。
- 控制台鉴权是配置文件的静态账号，无密码策略/失败锁定/审计留痕。暴露到更大范围前应接企业统一登录。
