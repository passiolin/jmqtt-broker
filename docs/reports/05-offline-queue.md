## 一、本阶段修的是一个功能缺口

不是增强，是**漏掉的功能**。

MQTT 规范里，对 `cleanSession=0` 的客户端，服务端在它离线期间**必须**为 QoS 1/2 的
订阅缓存消息，并在它重连后投递。

在此之前，本实现对这一场景是**直接丢弃**：

```java
// InternalSendServer.sendPublishMessage 的朴素实现
Channel channel = connectionRegistry.get(subscriberId);
if (channel == null || !channel.isActive()) {
    continue;   // ← 离线即丢
}
```

也就是说，**QoS 1/2 的投递保证在最需要它的场景（客户端掉线）下根本没有兑现**。
设备网络抖一下、或者后台被系统回收几分钟，期间的下行指令就永久消失了，
而且客户端那边毫无感知 —— 它只知道自己断过一次线。

**65 个源文件**（原 60 + 5），测试 **39 个单测 + 3 个端到端**。

## 二、三条丢弃口径

队列必须有明确的边界，否则写入量会失控。三条规则决定了哪些场景下保证成立：

| 场景 | 行为 | 原因 |
|---|---|---|
| QoS 0 | **不入队** | 它本来就没有投递保证, 离线即丢符合语义 |
| `cleanSession=1` 的会话 | **不入队** | 断开即消失, 缓存没有意义 |
| 持久会话 + QoS > 0 + 离线 | **入队** | 唯一需要兑现保证的场景 |

前两条是写入量的关键。**IoT 设备绝大多数用 `cleanSession=1`** —— 若把这两条写成
「都入队」，在百万连接下就是给每一个瞬时断开的设备都堆一份无人领取的消息，
既浪费内存也浪费 Redis 写入。

## 三、键结构

```
jmqtt:queue:{clientId}   List  按入队顺序保存序列化后的待投递消息
```

与 `session` / `subs` 共用 **hash tag `{clientId}`** —— 入队脚本要顺带读会话哈希的
`expire` 来设置 TTL，两者必须在同一 slot，否则 Redis Cluster 会直接拒绝这条脚本。

**TTL 取自会话哈希的 `expire` 字段**，而不是每次多查一次：队列的存活期本就该跟会话一致 ——
会话过期了，欠它的消息也没有意义了。

### 两个 Lua 脚本，都是原子操作

**入队**：RPUSH → 超限则 LTRIM 丢最旧 → 按会话 expire 续 TTL，一次往返完成。
拆成多条命令的话，并发入队会短暂突破上限，且 TTL 可能漏设。

```lua
redis.call('RPUSH', KEYS[1], ARGV[1])
local len = redis.call('LLEN', KEYS[1])
local max = tonumber(ARGV[2])
local dropped = 0
if max > 0 and len > max then
  redis.call('LTRIM', KEYS[1], len - max, -1)     -- 丢最旧
  dropped = len - max
end
local expire = redis.call('HGET', KEYS[2], 'expire')
if expire then
  local ttl = tonumber(expire)
  if ttl and ttl > 0 then redis.call('EXPIRE', KEYS[1], ttl) end
end
return dropped
```

**取出**：LRANGE + LTRIM 必须原子 —— 否则两个并发取队列会拿到重复消息。

## 四、几个刻意的设计选择

### 1. 为什么是「每客户端一条队」，而不是丢进 Kafka

我此前说过「消息的归宿是 Kafka」，这里需要把口径说清楚 —— 那是针对**数据面**
（上行遥测，一份数据多方消费）。而离线队列是另一回事：

> 一批消息**只欠给某一个确定的客户端**，且**必须保序**。

Kafka 的日志压缩保留的是每个 key 的最新值，不是队列语义；用它做每客户端队列需要
自己维护逐客户端 offset，复杂度远高于收益。按 clientId 分键的有序队列才是对的形状。

### 2. 丢最旧而非最新

IoT 场景下「最近的数据」通常比「最早的数据」更有价值。
考虑到这是对 QoS 保证的实际破损，丢弃**必须被计数并打日志**，绝不静默。

### 3. 分批投递而非一次取空

重连后按 50 条一批取。客户端在投递过程中再次断开时，尚未取出的部分仍留在队列里，
下次重连还能拿到。一次取空则这部分会随连接一起丢失。

### 4. 订阅是本节点私有的 → 入队只能发生在订阅所在的节点

这是「订阅不复制」这个架构选择的直接推论，值得明确：

- 客户端在节点 A 订阅后离线 → **只有节点 A 的 Trie 里有这条订阅**
- 发往该主题的消息若落在节点 B 上 → 节点 B 匹配不到任何订阅者 → 不会入队
- 发往该主题的消息若落在节点 A 上 → 节点 A 匹配到订阅、发现客户端离线 → 入队

所以正确的心智模型是：**离线消息由持有订阅的那个节点负责缓存**；
而客户端重连到哪个节点都能领到积压（队列在 Redis 里共享）。

### 5. 抽取了 `RedisConnectionManager`

会话持久化与离线队列都需要 Redis，也都要遵循同一套降级策略
（失败只记录不抛、状态变化才打日志、恢复后自动生效）。把这段逻辑复制到两个组件里，
迟早会有一处写得不一样 —— 而「有一处没降级」的后果就是 Redis 抖动直接抛到
MQTT 处理路径上。因此抽成了共享组件，`RedisSessionRepository` 改为委托它。

`InternalSendServerTest` 覆盖的正是三条丢弃口径与投递行为：

| 用例 | 验证内容 |
|---|---|
| 在线时直接投递，不入队 | 正常路径 |
| **离线 + 持久会话 + QoS 1 → 入队** | **唯一需要兑现保证的场景** |
| 离线 + QoS 0 → 不入队 | 写入量控制 |
| 离线 + `cleanSession=1` → 不入队 | 写入量控制 |
| 本地无该会话 → 不入队 | 防御性 |
| 不匹配的主题不产生入队 | 路由正确性 |
| 重连后投递积压并清空队列 | 核心链路 |
| **连接已断时停止投递，剩余积压留在队列里** | **保证中途断线不丢** |
| **超限时丢弃最旧的并计数** | 边界行为 + 可观测性 |

新增的两条接管用例钉住了队列的归属：
**非持久队列在接管时清理**（客户端已迁走，本节点再也投不出去）、
**持久队列在接管时必须保留**（已随会话归属新节点，删掉等于销毁新节点该投递的消息）。

### 离线消息跨节点投递（真实 Redis + 两节点）

**7 / 7 PASS。** 环境：Redis 8.0.6，nodeA:1883、nodeB:1884 共享该 Redis。

```
[PASS] 节点 A 建立持久会话
[PASS] 节点 A 订阅 offline/+/data 完成
[PASS] 客户端已离线(cleanSession=0, 会话与订阅保留)
[PASS] 离线期间已发布 3 条 QoS 1 消息
[PASS] 重连到节点 B 时 sessionPresent=true
[PASS] 重连后收到全部 3 条离线消息
[PASS] 离线消息保持入队顺序
```

这条链路**跨越了两个节点**，是本次最有价值的一条：消息在 **nodeA** 发布并由
nodeA 入队（因为订阅在 nodeA），客户端重连到 **nodeB** 后从共享的 Redis 队列里
领走全部 3 条且顺序正确。它同时证明了「订阅本地化 + 队列共享」这套组合是自洽的。

测试后 Redis 中只剩 `session` 与 `subs` 两个键，队列键已被消费掉 —— 也印证了
投递后队列确实被清空，没有泄漏。

日志侧也可见两侧行为：nodeA 打出入队日志，nodeB 打出投递日志。

## 六、为什么没做「在途消息持久化」

本阶段原计划一次解决两个问题，实际只做了离线队列。原因是**在途消息的持久化成本结构不同**：

| | 离线队列 | 在途消息 |
|---|---|---|
| 写入时机 | 客户端**离线**时 | 每条 QoS 1/2 消息发送时 |
| 写入频率 | 与「离线客户端的消息量」成正比 | **与 QoS 1/2 投递量成正比** |
| 结论 | 低频, 同步写完全可以接受 | 高频, **每条一次持久写** |

对后者，只有两条路，都必须先做决策：

1. **同步写** —— 保证不丢，但每条 QoS 1/2 消息都要等一次 Redis 往返，
   直接抬高投递延迟
2. **写回（异步/批量）** —— 投递路径不等 Redis，但节点崩溃时会丢最近一小批
   （窗口 = 回写间隔）

这与我一路坚持的「不让高频写落在外部存储上」是同一个取舍，不能顺手就做决定。
**更重要的是：先量一下 QoS 1/2 的实际占比。** 如果设备侧以 QoS 0 为主、
只有下行指令用 QoS 1，那同步写的开销可以忽略，直接选方案 1；
如果上行也用 QoS 1，就必须走方案 2 并明确接受窗口。

所以把它留成独立一项，附带这个决策依据 —— 而不是先实现了再回头解释代价。
