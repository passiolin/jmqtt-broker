## 一、接收方向 QoS 2 去重

### 之前的缺口

QoS 2 的「恰好一次」是**双方各自保证**的：发送方保证不重复发送，接收方保证不重复投递。
之前只做了一半 —— 客户端在拿到 PUBREC 之前带 `dup=1` 重发同一个报文标识符是**合法行为**
（PUBREC 可能丢在路上），而服务端因为没记住「这个标识符我已经收过」，会把它投递两遍。

后果很具体：同一台设备收到两条相同的控制指令（开关被切了两次、计量被重复记账），
而发布方从协议层看到的是**两次成功确认**，完全无从察觉。

### 实现

新增 `store/IInboundQos2Store` 与进程内实现 `InboundQos2Store`：

| 方法 | 时机 | 语义 |
|---|---|---|
| `mark(clientId, packetId)` | 收到 QoS 2 PUBLISH | `FIRST` 投递 / `DUPLICATE` 丢弃 / `OVERFLOW` 断连 |
| `release(clientId, packetId)` | 收到 PUBREL | 释放标识符，可再次用于新一轮流程 |
| `clearClient(clientId)` | 会话销毁 / 接管 / 过期回收 | 清除该客户端全部在途标识符 |

接入点：`PublishHandler`（投递**之前**判重）、`PubRelHandler`（释放）、
`ConnectHandler`（会话重建与脏状态清理）、`SessionTakeoverService`（跨节点接管）、
`SessionExpiryReaper`（会话过期回收）。

### 三个值得单独说的判断

**1. 释放这一步比去重本身更关键。**
只记不释放会让同一个标识符永久卡住 —— 客户端后续用它发的消息被当成重复而丢弃，
而且没有任何报错。**重复投递看得见（业务侧会发现指令执行了两次），静默丢弃看不见。**
所以实现上把释放放在回 PUBCOMP **之前**：若回包失败客户端会重发 PUBREL，而重发是幂等的；
反过来先回包再释放而释放失败，那个标识符就永久卡住了。

**2. 判重必须在投递之前。**
这一条看起来是显然的，但值得写下来：若先把消息投出去再判重，去重就完全失去了意义，
而且测试会「通过」（因为它只检查了是否重复投递，而不是检查副作用是否发生了一次）。
E2E 用例因此断言的是**订阅者收到的消息条数**，而不是某个内部状态。

**3. 每客户端上限不是武断的阈值，而是拿服务端自己声明的承诺去校验客户端。**
这个集合只会因为 PUBREL 或会话销毁而减少 —— 也就是说，**一个不发 PUBREL 的客户端可以让它
无限增长**，每次发一个递增的标识符即可，不需要任何越权行为。这是典型的内存放大攻击。

上限取「服务端在 CONNACK 里声明的 Receive Maximum」的两倍（下限 16）。超过它的客户端
本来就已经违反协议 —— `Receive Maximum` 的含义正是「你同时最多能有这么多条未确认的 QoS 1/2」。
留两倍余量是因为「声明值」与「实际遵守值」之间总有偏差，这一层的目的是防滥用而不是卡死正常客户端。

> 细节：`mark` 里必须**先判重再插入**。顺序反过来的话重复报文会先把计数推上去，
> 长连接上的正常重发会逐渐逼近上限，最终被误判为协议违规 —— 有一个专门的用例守这条。

### 验证

单测 `InboundQos2StoreTest` **8 / 8**，覆盖：首次/重复、**释放后可重用**、条目在清空后被摘掉、
客户端之间互不干扰、`clearClient`、超限返回 OVERFLOW、**大量重复不占用配额**、空 clientId 安全。

端到端 `tools/run-qos2-dedup.sh`（真实 broker + 裸 TCP 客户端）全部通过：

```
第 1 步  发 QoS 2(id=7)              → PUBREC ✓, 订阅者收到 1 条 ✓
第 2 步  未 PUBREL 前带 dup=1 重发    → PUBREC ✓, ★ 订阅者仍是 1 条 ✓
第 3 步  PUBREL(7)                   → PUBCOMP ✓
第 4 步  id=8 走完整流程              → 订阅者累计 2 条 ✓
第 5 步  ★ 重用 id=7 发新消息         → 订阅者累计 3 条 ✓(未被误判为重复)

订阅者收到: [first, second, third] —— 没有重复的 first, 也没有丢失的 third
broker 日志: "QoS 2 重复 PUBLISH, 已丢弃(只回 PUBREC) clientId=q2-pub packetId=7"
```

第 5 步是反向用例：它验证的是「**没有**把本该投递的消息丢掉」。两个方向都测，
是因为这个组件的两种失效方式严重程度不同但都真实存在。

### 遗留（明确记录）

状态在进程内，**不跨节点重启**。规范把「已接收但未完成确认的 QoS 2 消息」列为会话状态的一部分，
因此严格说它应当随会话持久化。没有做的原因是：要覆盖的场景是「客户端在秒级内重发」，
而重启窗口内恰好出现「会话被恢复 + 客户端重发同一标识符」的概率极低。
若要补，做法与已有的在途镜像（`InflightPersistence`）同构 —— 它已经在处理镜像方向的那一半。

## 二、前端渲染冒烟测试

### 为什么需要它

打包能过只说明语法与依赖没问题，完全不说明**组件树能挂载、路由解析正确、模板表达式能求值、
以及编译期常量都注入齐了**。后端接口可以用 curl 逐条验证，前端不行 —— 它需要一个 DOM。

写这个测试的过程立刻抓到一个真实缺陷：`baseOptions` 里**漏了 `process.env.NODE_ENV`**。
Vue 的 bundler 构建里到处是 `if (process.env.NODE_ENV !== 'production')` 形式的开发期检查，
而 esbuild 不像 Vite 那样自动注入它 —— 浏览器里 `process` 不存在，应用一加载就 `ReferenceError`。
**构建成功、页面全白**，是最难查的一类问题。

### 做法

`frontend/tests/render-smoke.mjs`：用 happy-dom 造 DOM，把**真实构建产物**挂上去再断言渲染结果。
编译用的是与 `npm run build` **完全同一份**插件（`vue-plugin.mjs`）—— 否则「测试那套配置能跑」
并不能说明发布的那套能跑。

覆盖 **6 组 35 项**：登录页、集群总览（节点卡片/广播形态/告警/重叠检查入口）、
**Redis 不可达横幅**、客户端表格、主题表格（跨节点标注）、排水向导；每组都断言「无脚本错误」。

### 环境上的两个坑（都记下来，因为会重复遇到）

1. **这个沙箱里 WebAssembly 不可用。** `WebAssembly.Memory()` 报 `could not allocate memory`
   —— 4GB `ulimit -v` 硬上限 vs V8 为 Wasm 预留的守卫区。`ulimit -v` 无法提升，
   `--no-wasm-trap-handler` 在这个 Node 构建里不存在，V8 标志也不允许放进 `NODE_OPTIONS`。
   后果：任何触碰 `fetch`（undici 用它解析 HTTP）的库在加载阶段就会崩。
2. **jsdom 30 直接依赖 undici，加载即崩**；`happy-dom` 可用，但它在加载完成后会由某个后台
   定时器异步预热一个 HTTP 解析器并撞上同一个限制。解法是：只吞掉「消息里含 WebAssembly」
   的那一种 `uncaughtException` 并计数，**其它异常照常让测试失败**。

### 顺带

抽出了 `frontend/vue-plugin.mjs`（构建与测试共用同一份 SFC 编译逻辑）；
`package.json` 增加 `npm test`。
