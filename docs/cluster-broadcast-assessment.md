# 方案评估：Kafka 差异化消费组做 MQTT 集群广播

> 评估时间：2026-09-11
> 命题：每个 broker 只保存自己的 topic 路由信息；publish 时写入 Kafka；其他节点用**不同 group.id** 消费同一 topic 实现广播
> 评估角度：**方案本身的设计可行性**（不针对任何具体 broker 的实现细节）

---

## 一、机制层面：成立，且是 Kafka 官方定义的一等语义

Kafka 官方文档原文：

> Consumers label themselves with a consumer group name, and each record published to a topic is delivered to one consumer instance within each subscribing consumer group.
> If all the consumer instances have the **same** consumer group, then the records will effectively be **load balanced** over the consumer instances.
> If all the consumer instances have **different** consumer groups, then each record will be **broadcast to all the consumer processes**.

所以「每节点一个独立 group.id → 每个节点收到全量消息」是 Kafka 设计的原生用法，不是绕路。同时它顺带解决了两个衍生问题：

- **共享订阅**：MQTT 的 `$share/{group}` 语义（同组内选一个）与 Kafka consumer group 的语义**完全一致**，可以直接映射
- **成员变更**：新节点加入只需分配一个新 group.id，无需改动其他节点的任何配置

---

## 二、这个方案的定位：它是第三种范式

参考现有的两种集群实现范式：

| 范式 | 做法 | 状态复制粒度 | 投递方式 |
|---|---|---|---|
| **复制元数据**（共识式） | 订阅表/客户端状态复制到所有节点 | 复制「谁订阅了什么」——小状态、高频变更、强一致 | 本地决策 + 定向投递 |
| **互联广播**（gRPC 全互联） | 订阅不复制，发布时向所有节点扇出 | 不复制状态 | 全量扇出 + 本地匹配 |
| **你的方案**（Kafka 广播） | 订阅不复制，发布走 Kafka，各节点独立消费全量 | 不复制状态 | 全量扇出 + 本地匹配 |

**你的方案在范式上等同于「互联广播」，但把传输层从 gRPC 全互联换成了 Kafka。**

这是理解它价值的关键：它保留「不复制元数据」的全部好处（无僵尸状态、无 quorum、重连风暴不产生共识写入），同时修掉了互联广播的两个结构性缺陷：

| 互联广播的结构性缺陷 | Kafka 方案是否解决 |
|---|---|
| 发布路径**同步等待最慢节点**（扇出结果要用于判定订阅者数量） | ✅ 解决。写入 Kafka 即返回，慢节点只体现为 consumer lag |
| 扇出压在 **broker 的网卡**上，无法横向扩展 | ✅ 解决。扇出压力转移到 Kafka 集群，可加 broker/partition |

## 三、成本结构：精确算一遍，别用「扇出总量不变」这种模糊说法

设全集群消息率 `M`、节点数 `N`、消息大小 `s`。

### 互联广播（gRPC 全互联）

一条消息被发到除来源外的所有节点，每节点都要把**自己产生的**消息发给其他 `N-1` 个节点。

```
每节点出向 = (M/N) × (N-1) ≈ M
每节点入向 = 来自其他节点的全部消息 ≈ M
每节点总网络 ≈ 2M          ← 与 N 无关
```

注意这个反直觉的结果：**每节点的网络负担与节点数无关**。节点多了，每个节点分担的发布量变小，但扇出倍数变大，两者抵消。

### Kafka 广播

```
每节点出向 = M/N                      （只写一次到 Kafka）
每节点入向 = M                        （从 Kafka 读全量）
每节点总网络 ≈ M(1 + 1/N) ≈ M
Kafka 侧   = 入 M、出 M×N              （在可横向扩展的基础设施上）
```

### 结论

| | 互联广播 | Kafka 广播 |
|---|---|---|
| 每 broker 网络 | 2M | **M（减半）** |
| 出向的 (N-1) 乘数 | 有 | **消失**（加节点不增加每节点出向） |
| 每节点入向 | ≈M | ≈M（**不变**） |
| N×M 扇出压在哪 | broker 网卡（不可扩展） | Kafka 集群（可扩展） |
| 扇出是否阻塞发布 | 是（等最慢节点） | 否（lag 异步） |
| 压缩 | 无 | 可开 snappy/lz4/zstd |

**两个必须说清楚的边界：**

1. **「每节点读全量」这个约束没有消失。** 每个 broker 仍然是全量消息的唯一消费者，单消费者吞吐（librdkafka 小消息约 50 万~100 万 msg/s）成为新的 per-node 上限。它从「网卡扇出瓶颈」变成了「消费吞吐瓶颈」，但**依然是 per-node 上限**。这是方案的内生约束，不是 Kafka 的问题。
2. **扇出总量 N×M 没有消失**，只是转移到了 Kafka。Kafka 能横向扩展，所以这个转移是真正的收益——但前提是你的 Kafka 集群容量要按 N×M 规划，而不是按 M。

## 四、方案成立必须满足的六个条件

这些是**这个范式的内在要求**，与选用哪个 broker 无关。缺任何一条，方案就不成立或会出事故。

### 1. broker 必须能以「无集群状态」模式独立运行

broker 要能只维护本地路由表、只服务本地客户端，并且**关掉一切内建的集群状态复制**。

如果同时开着内建的集群功能，就会形成双路径投递（Kafka 一份 + 内建集群一份），`E` 值直接翻倍。

### 2. 必须有回环防护（这是该范式自带的坑）

链路是 `本地投递 → 导出 Kafka → 各节点导入 → 本地投递`。**导入后再触发导出，就会形成回环。**

对一个「每节点消费全量」的拓扑，回环是指数级的：

```
节点1 发布 → Kafka 1 条
  节点2/3 各消费 1 条 → 各再导出 1 条 = Kafka 2 条
    三节点各消费 2 条 → 各再导出 2 条 = Kafka 6 条
      → 18 → 54 → …… 指数
```

**必须在导出侧过滤「来源 = 消息总线」的消息**（即标记来源，导出时跳过）。这不是可选优化，是方案的必要组成部分。

### 3. MQTT 主题必须放在**消息维度**，不能放在 Kafka topic 维度

如果把 MQTT 主题映射到 Kafka topic 名（例如 `mqtt/${topic}`），百万级 MQTT 主题就会变成百万级 Kafka topic —— 元数据爆炸、不可运维。**必须用单一的（或少量）Kafka topic，MQTT 主题放在消息里。**

### 4. MQTT 主题必须放在 **key**，不能放在 header

- Kafka 的默认分区器：**key 为 null 时按 sticky 策略分区**，同一个 MQTT 主题的消息会散落到不同 partition
- Kafka **只保证同一 partition 内的顺序**，跨 partition 无序
- 后果：同一设备的消息在不同 broker 上投递乱序

对上行遥测可容忍，对下行命令（开关、控制、OTA 触发）是事故。

**用 MQTT 主题做 key**，默认分区器会对 key 取 hash → 同一主题恒定落到同一 partition → 顺序有保证。同时 key 也顺便解决了「主题如何随消息传递」的问题（消费端从 key 还原主题）。

注意：**不要手工指定 partition**，那会让所有消息挤到一个 partition，既丢并发也丢顺序。

### 5. 广播的消费组必须与共享订阅的消费组隔离

这是一个真实的设计冲突：

- **广播**要求「每节点一个独立 group」→ 每个 group 都读全量
- **共享订阅**要求「同 group 内只被一个节点消费」→ 组内分摊

这两个需求在**同一个 Kafka topic 上互斥**。如果混在一个 topic：

- 想广播 → 共享订阅消息被每个节点都收到 → 每条共享消息被投递 N 次
- 想共享 → 广播消息被组内分摊 → 大部分节点收不到

**解法：分 topic。** 普通订阅消息走「广播 topic」（每节点独立 group），共享订阅消息走「共享 topic」（同名 group）。或者用两条独立的 topic 分别承载 `$share/` 与普通订阅。**这一点必须在方案设计阶段就确定，不能留到实现时。**

### 6. 必须自控 offset 提交

`enable.auto.commit = false`，处理成功后再提交。否则消费失败/重启时会重复投递（Kafka 的语义是 at-least-once）。

## 五、方案的内生缺陷（无法通过实现规避，只能权衡或应用层兜底）

1. **弱一致：clientId 全局唯一无保证。** 两个 broker 可能同时接受同一个 clientId → 「双连」窗口 → 重复投递。
   - 可兜底：应用层按设备 SN + 消息时序去重。上行数据通常幂等；下行命令需要幂等 ID。
2. **无跨节点会话恢复。** 节点宕机，其客户端会话、QoS 1/2 in-flight 消息、离线消息随内存一起消失。
   - 可兜底：会话/消息存储外置到 DC 内可跨节点访问的存储（Redis），与「不跨 DC 同步」原则不冲突——这里说的是 DC 内共享。
3. **延迟增加。** producer → Kafka → consumer 一跳，同 AZ 约 5~20 ms。MQTT QoS 1/2 下行端到端多 10~40 ms。IoT 场景通常可接受。
4. **Kafka 成为跨节点投递的单点依赖。** Kafka 不可用时，各 broker 的本地投递仍正常，但跨节点投递全断。
   - 相对 Raft 而言这是「换了一个单点」：从「quorum 可用性」换成「Kafka 可用性」。Kafka 通常有成熟的运维体系，但你必须接受它进入 MQTT 集群的关键路径。
5. **每节点消费全量 → 单消费者吞吐成为 per-node 上限**（见 §3 边界 1）。

## 六、判断这个方案是否合适：先测一个指标

**定义 `E` = 一条消息平均需要投递到几个节点**（按消息的订阅者去重后的节点数）。

| `E` 的取值 | 含义 | 方案是否合适 |
|---|---|---|
| `E ≈ N` | 每个节点都有订阅者 | ✅ 广播是必须的，方案接近最优 |
| `E ≈ 1` | 订阅者集中在一处 | ❌ 广播浪费 N 倍，应改用定向投递 |
| 中间值 | 部分节点有订阅者 | ⚠️ 需权衡，`E` 越低越亏 |

**测量方法**：在真实 topic 设计下，对每条发布的 MQTT 主题做本地 Trie 匹配，统计命中的订阅者去重后的节点数，取长期分布。这个数据必须来自你自己的业务拓扑，不能估算。

**为什么这是第一指标**：方案的扇出成本是 `M × E × s`。`E` 决定了「N-1 倍扇出」里有多少是有效投递。如果 `E ≈ 1`，你付了 N 倍的钱办了 1 倍的事。

一个典型的错配场景：云端业务系统连在某一个 broker 上订阅 `device/+/data` 收全量设备数据。这时 `E = 1`（只有那一个节点有订阅者，但每条消息都要扇给所有 N 个节点）。**这种情况下应该把数据面从 MQTT 订阅改成 Kafka 消费，而不是优化集群广播。**

---

## 七、一个可以保留的方案变体：把「全量广播」降级为「目录 + 定向」

如果测出来的 `E` 明显小于 N，方案不必推倒重来，只需要加一层轻量目录：

- 用 **Kafka compacted topic**（`cleanup.policy=compact`）维护 `MQTT 主题过滤器 → 节点集合`
- value 是节点集合，大小受 `N` 约束（不是受客户端数约束），压缩友好
- 每个 broker 消费全量目录，在本地重建一棵 `filter → nodes` 的 Trie
- 发布时先查本地目录得出目标节点集合，再只发给这些节点

这样：

- 保留了「不复制订阅表」的核心优点（目录只记 filter→nodes，不记 client）
- `E = 1` 时扇出也是 1，浪费消除
- `E = N` 时退化为全量广播，与原始方案等价
- 仍然无共识、无 quorum：Kafka 保证**同一 key 在同一 partition 内有序**，所以同一个 filter 的多次更新有明确全序，直接按时间戳裁决即可，**不需要共识算法**

代价是需要自己实现（改造 broker 的路由层 + 目录维护逻辑），复杂度高于纯桥接方案。

---

## 八、结论

**方案可行。** 机制层面是 Kafka 的原生语义，范式层面它保留了「不复制元数据」的全部优点，同时修掉了互联广播的两个结构性缺陷（同步阻塞、扇出压在 broker 网卡上）。

**但它不是免费的，有三件事必须先想清楚：**

1. **`E` 值是多少。** 这决定方案是「接近最优」还是「付 N 倍钱办 1 倍事」。必须用真实拓扑测，不能估。
2. **六个必要条件里，第 2 条（回环防护）和第 5 条（共享订阅的组隔离）是设计缺陷高发区。** 这两条在方案设计阶段就要定，不能等实现时补。
3. **每节点读全量这个约束不会消失。** 单消费者吞吐会成为新的 per-node 上限，容量规划要按这个算，不是按网卡算。

**什么情况下这个方案是最优解：**
- 订阅分布分散（`E` 接近 `N`）
- 重连/订阅变更频繁（元数据复制类方案会在这里崩，而本方案完全不受影响——重连只产生本地 Trie 写入）
- 发布频率中低，扇出成本可承受
- 不想承担 quorum 风险

**什么情况下不该用：**
- 订阅集中（`E ≈ 1`）→ 应先做「数据面走 Kafka 消费、不走 MQTT 集群」的架构调整，而不是优化广播
- 发布频率极高（例如百万设备每秒一次）→ `N` 倍扇出压不住，需走变体方案或重新设计
- 需要严格的 clientId 全局唯一 → 需要额外机制补充

## 附：必须回答的设计问题清单

在进入实现前，这 8 个问题都应该有明确答案：

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | 真实的 `E` 值分布是多少？ | 决定方案是否合适的第一指标 |
| 2 | 导出侧如何识别并跳过「总线来源」的消息？ | 不做 → 指数回环 |
| 3 | MQTT 主题用 key 还是 header 传递？ | header → 跨 broker 乱序 |
| 4 | 广播 topic 与共享订阅 topic 如何拆分？ | 同 topic 上两种语义互斥 |
| 5 | offset 提交策略？（建议手动提交） | 自动提交 → 重复投递 |
| 6 | retain 消息走哪条链路？ | 建议独立用 compacted topic，混进广播 topic 会导致新节点重放历史 |
| 7 | 节点宕机后其客户端的会话/离线消息如何恢复？ | 本方案无跨节点会话恢复，需外置存储 |
| 8 | Kafka 不可用时的降级行为是什么？ | 跨节点投递全断，本地应仍正常 |
