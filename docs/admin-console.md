# 管理面设计：Redis 作为控制平面

> 本文说明 jmqtt-admin 与 jmqtt-broker 之间如何协作，以及为什么这样协作。
> 涉及三个概念：**控制平面（Redis）**、**状态发布（broker 侧）**、**命令通道（admin → broker）**。

---

## 一、管理面为什么走 Redis，而不是 admin 直连各 broker

控制台要的是「整个集群的视图」，而它自己不在集群里。让它逐个 HTTP 请求各节点有两个问题：

1. **控制台必须能访问每个 broker 的管理端口。** 生产里这些端口通常不在同一张网内（它们往往只对内网管理段开放），而 Redis 是双方都必须能到的 —— 它本来就承担着跨节点会话持久化。
2. **「视图」被拆成了 N 次 RPC。** 任何一次失败都会让页面残缺，而残缺的视图比看不到更危险：运维会以为「那个节点没有客户端」。

改成从 Redis 读之后，**「节点是否可达」由心跳是否存在表达，而不是由请求是否超时表达**。后者无法区分「节点挂了」与「网络抖了一下」，前者可以精确到秒。

一个附带的好处是：**控制台重启不影响任何进行中的运维动作**。驱逐是 broker 在执行，控制台只是在旁边看进度。

## 二、Redis 键布局

这是一份**契约**，且没有编译期检查 —— broker 侧的 `AdminRedisKeys` 与控制台侧的 `AdminKeys` 必须保持一致。两个工程是独立的 jar，唯一把它们绑在一起的就是「键长什么样」。

| 键 | 类型 | 内容 | TTL |
|---|---|---|---|
| `{prefix}:admin:nodes` | SET | 全部曾注册过的节点 id | 无 |
| `{prefix}:admin:node:{nodeId}` | HASH | 心跳 + 节点概要 | `state-ttl-seconds` |
| `{prefix}:admin:clients:{nodeId}` | HASH | `clientId → 紧凑 JSON` | 同上 |
| `{prefix}:admin:filters:{nodeId}` | HASH | `topicFilter → 订阅者数` | 同上 |
| `{prefix}:admin:cmd:{nodeId}` | LIST | 控制台下发的命令 | 无（有长度上限 + 命令自带时效） |
| `{prefix}:admin:cmdr:{cmdId}` | HASH | 命令结果与进度 | `command-result-ttl-seconds` |

三个关键设计点：

**1. TTL 就是「节点还活着」的唯一依据。** 节点每 `heartbeat-interval-ms` 重写一次概要并给三个状态键续期；进程消失后键自然过期，数据一并消失。不需要任何「死亡通知」机制，也就不会出现「节点崩了但视图里还挂着一堆幽灵客户端」。

> ⚠️ 续期这一步容易漏：Redis 里 `HSET` **不会**刷新键的 TTL。节点若忘了显式 `EXPIRE`，数据会在 TTL 到点后整体消失，而节点还在正常跑 —— 表现为控制台里节点时有时无。

**2. 命令用 LIST 而不是 Pub/Sub。** Pub/Sub 是「此刻在线的订阅者才收得到」，节点可能在断线重连的瞬间错过命令，且没有任何补偿。对一条「驱逐」指令来说，「可能收不到」和「一定收到或明确过期」差别很大。

**3. 键按节点分片。** 客户端注册表按 nodeId 分键，而不是全集群一个 hash —— 不同节点的生命周期本就独立（TTL 各自算），也避免所有节点的写入挤在同一个键上。

## 三、三种数据的更新方式，各自不同

| 数据 | 写入方式 | 为什么 |
|---|---|---|
| 节点概要 | 心跳周期全量覆盖 | 字段少、变化慢，全量覆盖最简单；它同时承担「节点还活着」的信号 |
| 客户端注册表 | 连接/断开时增量 `HSET`/`HDEL` | 十万级条目，全量重写太贵；单条变更本身很便宜 |
| 订阅过滤器视图 | 变更后从主题树重算 | 见下 |

### 过滤器视图为什么是「重算」而不是「增量计数」

增量计数的诱惑很大：订阅时 `HINCRBY +1`、退订时 `-1`，开销极小。但它有一个无法回避的问题 —— **同一件事可能被写两次**：

- 会话从持久层恢复时会把订阅重新写回本地主题树（那批订阅其实早就在了），增量计数会把它算成新增；
- 节点重启后本地树是空的，而增量计数却从 Redis 上的旧值继续累加。

于是计数只会越漂越远，而**漂移是不可自愈的**：没有任何时刻能确定「现在这个数是对的」。

改成从本地主题树重算之后，漂移在结构上不可能发生 —— 树是唯一事实来源。代价是一次遍历，所以用**订阅变更版本号**做闸门：版本没变就直接跳过（空闲节点不做任何无用功），变更后按 `filter-publish-interval-ms` 合并多次变更只算一次。

### 客户端注册表为什么必须增量

十万条目的全量重写是几十 MB 的传输，无法按秒级频率做。所以它是增量的，并靠三种时机**对账**来消除偏差：启动时、Redis 重连后、发现增量被丢弃时。

对账做的是「先 `DEL` 再分块写回」。为什么必须 DEL：只做增量补齐的话，「曾经连过但后来因故没发出 HDEL」的条目会永远留在那里成为**幽灵客户端**。

### 绝不阻塞 MQTT 处理路径

连接建立/断开只做一件事：**往有界队列里塞一个元素**，然后立刻返回。真正的 Redis 写入在独立的守护线程上以批量管道的方式完成。队列满时丢弃并计数 —— 丢掉的增量不会造成永久偏差，因为对账会把它纠正回来。

有一个细节必须挂在同一个判断上：

```java
boolean removed = connectionRegistry.unregister(clientId, channel);
if (removed) {
    adminStatePublisher.clientOffline(clientId);
}
```

否则「旧连接的延迟关闭」回调会把刚接管它的新连接从视图里删掉 —— 客户端明明在线，控制台上却消失了。

## 四、命令通道

**控制台除了往命令队列里放东西，不修改任何 broker 状态。** 这意味着即使控制台被误操作或出现 bug，最坏后果也只是「下发了一条不该发的命令」，而不会出现「控制台把某台机器的状态改坏了」。

### 命令自带签发时间与最大年龄

命令走 Redis 列表，没有 TCP 那样的连接状态保证时效。于是出现一个必须处理的情况：**节点离线期间控制台下发了命令，一小时后节点起来了，把这条命令取出来照常执行。**

对「查看状态」没有影响，但对「驱逐」后果严重 —— 一小时后执行的驱逐打的是完全不同的流量形态，而且此时操作者多半已经忘了自己下发过它。所以每条命令带 `issuedAt` 与 `maxAgeMs`，由**节点侧**做超龄拒绝。

> 把超龄判断放在节点侧而不是控制台侧，是因为只有节点知道「我是什么时候取到这条命令的」。控制台侧的「以为过期了就不发」解决不了队列里已经躺着的那一条。

### 为什么用非阻塞轮询而不是 BRPOP

Blocking 版本看起来更优雅 —— 有命令立刻醒，没命令零开销。但它有一个致命的副作用：**Lettuce 的多个命令复用同一条 TCP 连接**，而阻塞命令会把这条连接占住直到它返回。于是这个 poller 会在每次 BRPOP 期间，把会话读写、在途镜像、离线队列全部堵在身后 —— 一个「每 500 毫秒查一次管理命令」的组件，变成了 MQTT 处理路径上的间歇性停顿。

轮询的代价是多几百毫秒延迟。对一条人工触发、随后还会被持续观测进度的驱逐命令来说，这完全无所谓。

### 队列必须有长度上限

连点按钮这类操作会让队列增长，而节点一次只取一条。没有上限时，一次误操作可以在队列里留下几百条命令，之后节点会一条条取出来、一条条判定过期 —— 那段期间真正的命令要排队。因此控制台 `LPUSH` 之后立刻 `LTRIM`。

## 五、排水流程

「把某节点上的客户端迁走」横跨了四件不同系统里的事：负载均衡停止调度（人做的）、broker 断开连接、客户端自行重连、连接在节点间重新分布。**没有任何一个系统能单独回答「现在到底成没成」**，所以流程状态机放在控制台。

```
① 建立基线        记录各节点当前连接数 —— 没有基线就无法回答「迁走了多少」
② 预检            观测一段时间，看新连接是否还在进来
③ 人工确认已停调度  负载均衡不受控制台控制，只能由人操作并确认
④ 分批驱逐        交给 broker 执行，控制台只观察进度
⑤ 等待并校验重连   看目标节点是否下降、其他节点是否上升
⑥ 结论            完成 / 超时（附具体诊断）
```

### ② 预检为什么不能省

如果负载均衡仍在向该节点调度新连接，驱逐就变成一个**死循环**：断开的客户端立刻从同一个入口重连回来，控制台看到的是「驱逐一直在进行、连接数却始终不降」。没有预检的话，这个状态会一直持续到批量跑完，然后报一个含糊的超时 —— 而真实原因（调度没停）一句话就能说清。

### ⑤ 为什么必须看「其他节点涨了没有」

只看目标节点连接数下降是不够的：客户端可能是被断开了但**根本没重连成功**（设备离线、证书过期、DNS 未更新）。那时目标节点确实变空，但业务其实已经中断 —— **「迁走了」和「连不上了」在单节点视角下长得一模一样**，必须靠其他节点的连接数上涨来区分。

### 超时诊断把两个维度组合起来

| 目标节点 | 其他节点 | 结论 |
|---|---|---|
| 没降 | — | 节点没执行命令：检查该节点是否启用管理面、日志里有没有「开始驱逐」 |
| 降了但不足 | 涨了 | 差额部分回连到了同一节点：确认停调度是否生效 |
| 降了 | 没涨 | 客户端尚未重连，或连到了未启用管理面的节点 |

用一段含糊的「超时」把三种情况混在一起，等于让操作者从头查一遍。

### 驱逐做什么、不做什么

**只关连接。会话、订阅、离线队列、在途镜像一律不动。**

这是整个操作能成立的前提：被驱逐的客户端重连到另一个节点后会走既有的「取得归属 + 跨节点接管」路径 —— 拿到 `sessionPresent=true`，订阅被恢复、离线积压继续投递、未确认的 QoS 1/2 以 `dup=1` 重发。反过来，如果顺手把会话删了，客户端重连后会以为自己是全新的，表现为「订阅没了、离线消息没了」—— 而这恰恰是驱逐本不该造成的破坏。

### 为什么要分批、限速、还有硬上限

一次性断开十万条连接会同时触发三件事：十万条遗嘱涌入路由与集群总线、十万次重连打向剩余节点、十万条会话的归属转移。任一件都足以把集群从「一次运维」变成「一次故障」。

所以有三个约束，且都是**安全阀而不是性能参数**，因此做在配置里而不是请求参数里（请求只能在配置允许的范围内调整）：

- `max-evict-per-task`（默认 5000）：硬上限，控制台与 broker 双重校验；
- `default-evict-batch-size` / `min-evict-interval-ms`：批次与间隔；
- 同一节点**严格串行**：两个任务并行时各自按自己的节奏断开，合起来的速率就不再是任何一方设定的值 —— 限速这件事只有在「谁在限速」唯一时才有意义。

### 遗嘱消息

关连接必然触发 `channelInactive`，而那里按规范要发布遗嘱。**默认按规范发布**（这是正确语义），代价是一次排水会产生一批遗嘱。`publishWill=false` 提供显式的跳过开关 —— 但它是「操作者在明确知道自己在做什么时的选择」，不是默认。

## 六、与集群广播开关的关系

管理面与广播开关是两件独立的事，但它们在同一个部署决定上交汇。

**广播开关解决的是「消息要不要跨节点」**：如果业务上只有设备与服务端通信（设备与其他端之间走 P2P 信令，本来就有成本更低、时效更好的方案），那么让每个节点消费全量消息就纯粹是成本。

配置形态：

| `broadcast-enabled` | `broadcast-filters` | 效果 |
|---|---|---|
| `true`（默认） | 空 | 全部主题都广播 —— 既有语义 |
| `true` | 非空 | 只有命中白名单的主题跨节点（例如只留端间信令与下行指令） |
| `false` | 忽略 | 不广播：只本节点投递 + 走数据面上行 |

**「关闭广播」与「配置漏了」必须是两个状态。** 所以关闭用独立开关表达，而不是复用「过滤器为空」—— 后者的语义是「全部广播」。反过来，过滤器全非法时**退化为全部广播**而不是全部拒绝：配置写错应当倒向安全的一侧。

关闭广播时有两件事不受影响，且**必须**不受影响：

1. **数据面上行**照常 —— 否则就是把「省成本」做成了「丢数据」；
2. **连接接管通道**照常 —— 它承载的是「同一 clientId 的旧连接该释放了」，属于会话正确性的一部分，与「跨节点 pub/sub 要不要做」是两个问题。一旦被误伤，表现为同一 clientId 在两个节点同时在线，业务侧看是「指令被处理了两次」这种极难定位的现象。

### 这个开关唯一的风险点，以及它为什么可以被验证

关闭广播后，若某个主题过滤器在**多个节点**上都有订阅者，那些订阅者将永远收不到消息 —— **没有报错、没有日志、发布方与订阅方都感觉不到异常**。

这正是控制台能回答的问题：每个节点的过滤器视图都在 Redis 上，把它们对起来看，重叠就是「需要跨节点投递」的证据。控制台的 `/api/topics/overlap` 做的就是这个检查。

于是「关广播」从一个凭信心的决定，变成一个可以被验证的决定。

## 七、错误处理的两种相反取向

| | broker | 控制台 |
|---|---|---|
| Redis 故障时 | **静默降级**：会话退化为新会话、镜像不落盘<br>首要目标是「接入必须一直可用」 | **明确报错**：顶部横幅 + `redis.reachable=false`<br>唯一的数据来源就是 Redis，连不上必须说 |

第二种不是洁癖。「客户端列表为空」可能是「集群真的没有客户端」，也可能是「Redis 连不上」—— 前者是正常状态，后者是故障。**把后者显示成前者，操作者会基于一个完全错误的判断去执行驱逐。** 所以控制台维护一个显式的可达状态，前端据它决定显示横幅还是空列表。
