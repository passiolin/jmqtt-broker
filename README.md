# jmqtt-broker（v3-lite）

面向 **IoT 设备 ↔ 服务端通信** 的 MQTT Broker。基于 Netty + Spring Boot，单模块 Maven 工程。

## 这个分支解决什么问题

标准 MQTT 的能力集合里，有一大类是给「客户端之间互相订阅」用的：主题通配符、  
共享订阅、订阅标识符、集群内的全量广播扇出。而 IoT 平台的真实形态通常是另一种：

```
设备  --上行-->  broker  --Kafka-->  服务端（业务系统 / 数仓 / 规则引擎）
设备  <--下行--  broker  <--Kafka--  服务端
```

**没有设备订阅另一台设备的主题**，也没有 APP 订阅设备。设备只做两件事：上报，  
以及接收针对自己的指令。所有跨端逻辑都在服务端完成，服务端连的是 Kafka，不是 MQTT。

这个判断一旦成立，集群里最贵的那一项就可以整块去掉——

### 被去掉的成本：跨节点广播扇出

常规集群做法是「每个节点都消费全量消息，再各自对本地订阅树匹配」。它能保证无论  
订阅者连在哪个节点都能收到，代价是 **N 个节点 = N 倍消息复制**：一条设备上报，  
三个节点各自反序列化、各自查一次订阅树、各自丢弃。

当订阅者只有服务端（而服务端连 Kafka）时，这 N-1 份工作全是浪费。所以本分支的默认  
部署形态是：

| 流量      | 走哪                    | 是否扇出    |
| ------- | --------------------- | ------- |
| 设备上行    | 直接进 Kafka，服务端消费       | **1 份** |
| 服务端下行指令 | Kafka → broker → 目标设备 | 1 份     |
| 连接接管通知  | 独立的定向通知通道             | 只发给旧节点  |

上行独占由 `uplink-exclusive: true` 落地：命中上行过滤器的消息写一次 Kafka 就不再
进集群广播。

双节点 4C8G、30 万连接、每设备每 60s 一条 QoS1 + 逐条回显，只改这两个开关：

| 指标 | ① 广播开 + 上行不独占 | ② 广播开 + 上行独占（默认） | ③ **广播关 + 上行独占** |
|---|---|---|---|
| 连接成功 / 失败 / 重连 | 287,254 / 1,811 / 2,187 | 299,858 / 448 / 849 | **300,000 / 402 / 1,528** |
| 30 万档 TPS | 4,988 | 5,409 | 4,973 |
| PUBACK P50 / P99 | **1,174 / 25,233 ms** | 545 / 34,628 ms | **128 / 7,583 ms** |
| 全环 RTT P99 | 110,058 ms | 61,203 ms | **15,100 ms** |
| 下行丢包 | 472,142（30.8%） | 233,340（23%） | **295（0.03%）** |
| broker-a CPU 峰值 | 98.0% | 99.9% | 99.3% |

三档的 CPU 峰值都在 98~99.3%，**没有区别**——这说明 CPU 打满不是广播造成的，
是 30 万连接 + 5k TPS 双向流量的固有成本。真正的差别在**延迟和丢包**：

- **② vs ①**：上行独占后 P99 没能改善（25.2s → 34.6s），下行丢包也只是从 30.8% 降到 23%。
  上行不再占 CPU 后，资源全被下行吃掉，队列积压反而更深。**只开上行独占是不够的。**
- **③ vs ②**：再关掉广播，P99 从 34.6s 降到 7.6s（**快 4.6 倍**），
  全环 RTT 从 61s 降到 15s，下行丢包从 23% 降到 0.03%。

结论：**广播关掉省的不是 CPU，是延迟和丢包**。CPU 在 30 万连接这个量级上
无论如何都会打满，此时省下来的每一点排队深度都直接转化为尾延迟。
单靠 `uplink-exclusive` 只能砍掉上行那份复制，跨节点下行的扇出还在，
必须两个一起关才能真正收敛。

> 如果将来确实出现「必须有跨节点 MQTT 订阅」的场景（比如 APP 直连 MQTT 订阅设备状态），
> 把 `broadcast-enabled` 改回 `true` 即可，代价是上表第 ② 列。
> 注意这个开关配错的症状是「消息静默不到」而不是报错——见「已知边界」第 6 条。

### 顺带的裁剪

协议只保留 **3.1.1（兼容 3.1）**。原因不是性能——实测 v5 分支根本不在热路径上——  
而是**每处回包只需维护一种字节形态**：

| 报文       | 3.1 / 3.1.1      | v5                  |
| -------- | ---------------- | ------------------- |
| CONNACK  | `20 02 00 00`    | `20 03 00 00 00`    |
| UNSUBACK | `B0 02 00 07`    | `B0 03 00 07 00`    |
| SUBACK   | `90 03 00 07 01` | `90 04 00 07 00 01` |

双栈意味着 CONNACK / PUBACK / SUBACK / UNSUBACK / DISCONNECT 每处都要按版本分支。  
v5 客户端在握手阶段被明确拒绝，而不是接受后静默降级——放行它只会让客户端收到  
结构错位的坏字节。

3.1 与 3.1.1 在报文层面等价（CONNECT payload 结构相同，各类回包字节布局相同），  
实测两者编出的回包逐字节一致，因此走同一条路径。差别只有两条：3.1 的 clientId  
限 1~23 字符（解码器直接拒），以及 3.1 的 CONNACK bit0 是保留位而非 Session Present  
（本实现这一位只在会话不存在时为 true，两种解读下都不产生误判）。

## 性能

### 测试口径

压测跑在单台 PVE 宿主上（Intel Xeon E5-2698B v3，16 核 32 线程 @ 2.0GHz），
**同时运行的虚拟 vCPU 总数是 74 个**——包括一台常年占 28 核的 GPU 工作站。
vCPU : 物理线程 ≈ **2.3 : 1**，属于明显超分。

这一节把这些数字能说明什么、不能说明什么，按实测的监控数据交代清楚，
因为下面所有结论的强度都取决于它。

**一、vCPU 饱和时，物理机还有大量空闲，所以容量绝对值被低估。**

以 EMQX 那轮判定撑不住的时段（18:05–18:16）为例，把 Prometheus 里两侧的数据
拉出来对比：

| 指标 | 数值 |
|---|---|
| 112（EMQX 虚拟机，4 vCPU）CPU | 峰值 **99.6%**，均值 37.8% |
| 其中纯计算 `user+system+softirq` | 峰值 **85.6%**（18:10 那一刻，同时 `iowait` 占 12.6%） |
| 其中 `iowait` | 峰值 63.3%（出现在 18:12），均值 10.9% |
| 其中 `steal`（等物理核的时间） | 峰值 **0.2%**，均值 0.1% |
| PVE 物理机整体 CPU | 峰值 **36.7%**，均值 17.0% |
| PVE 磁盘 `dm-9` / `dm-4` 利用率 | 峰值 94.4% / 85.5% |

最后两行的对照是关键：**虚拟机里那 4 个 vCPU 已经打满（99.6%），
而整台物理机的 32 个线程只用了 36.7%。**

这里必须把机制说准确，否则容易归错因：

- **不是「超分抢走了它的时间」**。`steal` 峰值只有 0.2%，它申请的 CPU 时间
  基本都拿到了，宿主没有克扣它。这也说明这套 2.3:1 的超分在 CPU 争抢上
  并没有实际伤到它——至少在这轮负载下没有。
- **是「核数不够」**。这台 VM 只配了 4 个 vCPU，所以它最多只能占物理机
  ≈ 4/32 的处理能力。它自己那 4 个核已经打满，而物理机剩下的算力就在那儿
  闲着，只是**没有 vCPU 去拿**。所以「物理核如果给足，4 个 vCPU 不会在
  这个负载下就饱和」这个判断成立——换核数更多、不超分的独占机型，
  容量会明显更高。

换句话说，这轮压测的容量上限是**虚拟机规格**给的，不是宿主机算力给的。

**二、但也不能反推「再加几个核就能到 30 万」。**

同一段曲线拆开看，它卡住的原因前后不同：

| 时段 | `user` | `iowait` | 状态 |
|---|---|---|---|
| 18:07–18:10 | 46~78% | **0** | 真的在算，算力见顶 |
| 18:11–18:12 | 17~29% | **47~64%** | 让出 CPU，在等盘 |

后半段磁盘写峰值 124 MB/s、宿主 `dm-9` 利用率 94.4%，是**真等盘**。
所以「物理机还有 63% 空闲」不能直接读成「给 EMQX 更多 CPU 它就能撑到 30 万」：
算力那一头加核有用，落盘那一头加核没用。这一轮数据回答不了
「换更好的盘 + 独占核之后能到多少」。

**三、EMQX 这类引擎的 CPU 百分比不能直接当"余量"读。**

这条是这次最实用的一条经验，和你在生产环境看到的对得上：**EMQX 的 CPU 利用率本身
就偏惰性**，它显示 100% 的时候，里头的成分可能完全不是"在算"。这次的实测就是例子：

| 时段 | 非 idle 总量 | 其中 `user+sys+softirq` | 其中 `iowait` |
|---|---|---|---|
| 18:08（建连接中） | 85.3% | **83.0%** | 0 |
| 18:10（仍在建连接） | 99.6% | **85.6%** | 12.6% |
| 18:12（卡死之后） | 97.7% | **38.4%** | **55.0%** |

同样是"CPU 快满"，18:08 是真的在算（83% 都在计算），18:12 已经有 55% 挂在等盘上。
所以**看这类引擎的瓶颈，得把 `iowait` 从 CPU 里拆出来**，否则会把"等 IO"
误读成"算力不够"，然后加核——加了也没用。

结论落到一句可操作的：**CPU 高 + `iowait` 低 = 真算力瓶颈，加核有效；
CPU 高 + `iowait` 高 = 先查 IO，加核无效。** 这次 EMQX 是前半段属于前者、
后半段属于后者，两段各卡一次。

**四、延迟抖动大**。vCPU 争抢会让 PUBACK P99 在轮次之间差出几倍
（同样配置，25s 与 34s 都出现过）。

综合以上，下面所有数字的定位是：**验证设计取舍的方向性，不做容量承诺**。

### 单机容量

**8C16G 单独测过，是这里的头两行**（跑在 111 上，之后 111 被改成 4C8G 用于双节点对比，
所以后面所有 4C8G 的轮次指的是改配置之后）：

| 场景 | 规格 | 结果 |
|---|---|---|
| 纯心跳（零业务消息） | **8C16G** | **40 万连接**，零失败零重连，CPU 峰值 48%，内存 6.4G（≈11KB/连接） |
| 业务闭环（上行 + 回显） | **8C16G** | 30 万连接 / 5,505 TPS，上行零丢失零重复，CPU 41%/73%，内存峰值 11.5G/12G 堆 |
| 业务闭环（上行 + 回显） | 2×4C8G 集群 | 30 万连接 / 4,973 TPS，下行丢 295 条（0.03%），P99 7.6s |
| 纯 MQTT 层（无 Kafka/Redis） | 4C8G | 30 万连接 / 6,371 TPS,  PUBACK P99 **186ms** |

单机 8C16G 这两行里有个值得注意的点：**业务闭环到 30 万时先到顶的是内存，不是 CPU**。
CPU 峰值 73%，内存已经吃到 11.5G / 12G 堆（72%~96%）。纯心跳 40 万连接只用 6.4G，
差距来自持久会话和下行队列。所以 8C16G 做业务闭环时，**16G 内存是比 8 核更先紧的配置项**，
要往上撑应该先加内存。

### 双节点集群：三档开关对比

同一台机器、同一份压测脚本，只改 `uplink-exclusive` 与 `broadcast-enabled`。
**这三档的对比是可信的**——它们在同一台机、同一时段、同一份脚本下完成，
宿主机超分对三档的影响是同向的，相对差异成立。

但要如实说一句宿主机的情况：这几轮里**宿主机 CPU 峰值到了 76.8% 和 84.6%**，
并且被测机有 2.1%~4.8% 的 `steal`（时间片被宿主抢走）。
所以下面这组数字的**绝对值是偏低的**，属于「宿主也快满」的条件下跑出来的结果。
三档之间的相对差异仍然成立，因为三档承受的是同一个宿主环境。

| | ① 广播开 | ② 广播开 + 上行独占 | ③ 广播关 + 上行独占 |
|---|---|---|---|
| 连接 ok / fail / 重连 | 287,254 / 1,811 / 2,187 | 299,858 / 448 / 849 | **300,000 / 402 / 1,528** |
| 上行丢失 / 重复 | 0 / 0 | 0 / 0 | **0 / 0** |
| PUBACK 到达率 | 99.38% | 99.9982% | **99.9930%** |
| 下行丢包 | 472,142（30.8%） | 233,340（23%） | **295（0.03%）** |
| broker CPU 峰值 | 98.0 / 95.3% | 99.9% | 99.3% |
| 宿主机 CPU 峰值 | 84.6% | 76.8% | 76.8% |

三档的 CPU 都在 98~99.9%，**差别不在 CPU**。30 万连接 + 5k TPS 双向流量
在这个规格上本来就会打满，此时能省的每一点排队深度都直接变成尾延迟和丢包。

### 与同类 broker 的对照

同机同场景（单节点 4C8G、10/20/30 万连接阶梯、每设备 60s 一条 QoS1、不回显）：

| | jmqtt-broker | EMQX 5.8.9（调优后） | RMQTT 0.24.0 |
|---|---|---|---|
| 连接建立 | 300,000 / fail 0 | **256,656 / fail 6,119** | 300,000 / fail 0 |
| 10 万档 PUBACK P99 | 53.7 ms | **7.6 ms** | 数 ms |
| 20 万档 PUBACK P99 | 54.3 ms | **21.6 ms** | 数 ms |
| 30 万档 PUBACK P99 | **186.6 ms** | 14,361 ms（未达到 30 万） | 29.9 ms |
| CPU 峰值（虚拟机内，4 vCPU） | 45.7% | **99.6%** | — |
| 宿主物理机 CPU 峰值 | 30.0% | 36.7% | — |
| 内存峰值 | 46.4% | 48.8% | — |

> 两台 VM 规格相同（都是 4 vCPU）。注意「物理机 36.7%」那一格是**宿主机**的数，
> 不是 EMQX 自己的——它自己是 99.6%。这两个数经常被混为一谈，但含义完全相反：
> 一个说明它已经满载，一个说明宿主还有余量。
>
> 这一组的宿主负载是**所有轮次里最公平的**：两边都在 30%~37%，
> 宿主既没成为瓶颈，也没给谁额外的余量。所以这组对比受超分干扰最小。

**关于 EMQX 这一栏，有六件事必须说清**，否则这个对比会被误读：

1. **上一版用的是默认配置，那组数字不成立**。EMQX 的 `vm.args` 里 `+P`（Erlang
   进程上限）是注释掉的，用 Erlang 默认的 262144。30 万连接约需 60 万进程，
   必然撑不到。本轮已显式配成 `process_limit = 2097152`、
   `max_ports = 1048576`、`max_connections = 1024000`，并确认生效
   （`erlang:system_info(process_limit)` 返回 2097152）。
2. **调优后依然停在 25.7 万，且这次它的 4 个 vCPU 是真跑满了**。接入速率在
   最后一段从 2000/s 掉到 30/s，伴随大批 `i/o timeout`（CONNECT 握手包排不上）。
   从 Prometheus 拉这 7 分钟的曲线：虚拟机内 CPU 峰值 **99.6%**。
   进程上限已经不是原因，它撞到的是自己的处理能力上限。
3. **但「跑满」在前后两段是两种不同的满**。逐点看时序：

   | 时段 | `user` | `system` | `iowait` | 在干什么 |
   |---|---|---|---|---|
   | 18:07–18:10 | 46~78% | 10~14% | **0** | 纯计算，建连接 |
   | 18:11–18:12 | 17~29% | 15~21% | **47~64%** | CPU 让位，在等盘 |
   | 18:13 之后 | 归零 | 归零 | 归零 | 压测结束 |

   前半段是**真在算**（`user` 打满，`iowait` 为 0）；后半段变成**挂着等盘**
   （`iowait` 冲到 63.3%，磁盘写 124 MB/s，宿主 `dm-9` 利用率 94.4%）。
   所以它不是单一原因卡住的：**先是算力见顶，接着落盘也顶上来**。
4. **同一时段宿主机只用了 36.7% 的 CPU，`steal` 只有 0.2%**。这两件事一起看
   才是完整结论：超分并没有在 CPU 上抢它的时间（被偷走的时间可忽略），
   它缺的是**核数本身**——VM 只有 4 个 vCPU，最多只能占物理机 4/32 的处理能力，
   剩下的算力闲着也没有 vCPU 去拿。**所以「物理核给足，4 个 vCPU 不会在这个
   负载下饱和」这个判断成立，但机制是核数不够，不是被抢占。**
   这轮压测的容量上限是**虚拟机规格**给的，不是宿主机算力给的。
5. **也因此不能说「加核就能到 30 万」**。后半段等盘那部分，加 CPU 解不开；
   真要提容量，CPU 和盘得一起上。这一轮数据回答不了「换更好的盘 + 独占核
   之后能到多少」。
6. **EMQX 在小规模下确实更快**。10 万/20 万档 P99 是 7.6ms / 21.6ms，
   jmqtt 同档位是 53.7ms / 54.3ms。Erlang 的轻量进程 + 抢占式调度在未饱和时
   延迟控制更好。jmqtt 的优势在**高连接密度下的承载能力**——
   到 30 万档 EMQX 的 P99 涨到 14.4s 且建不满，jmqtt 仍是 186.6ms。

> 结论：**不要把这个表当成「谁更强」的排名**。它只说明两个引擎的特性差异，
> 而且两台机器共享同一台超分的宿主机。要出权威对比，需要独占物理机、
> 双方都调到各自推荐配置、多轮取中位数。

## 存储选型：建议用 Valkey

Redis 在本项目里只做**持久会话与在线归属**，不承载消息投递——投递路径全部走进程内存。  
用到的命令只有基础几类：

```
HSET / HGET / HGETALL / HDEL    会话属性、订阅关系
LPUSH / LTRIM                   离线消息队列（有界）
INCR / EXPIRE / DEL             报文标识符、TTL
SET / GET                       在途镜像快照
EVAL                            少量原子操作（归属转移）
```

**这些 Valkey 全部兼容，零代码改动即可替换。**

推荐 Valkey 的理由：

1. **许可**：Valkey 是 Linux 基金会下的 BSD-3 项目，源自 Redis 7.2.4 的分支。  
   Redis 在 7.4 起改为 RSALv2 / SSPLv1 双许可，自建对外提供服务属于受限场景。  
   Valkey 没有这个问题，也不会有后续许可变动。
2. **性能与内存**：延续 Redis 的 IO 多线程与数据结构，同等负载下表现一致；  
   本项目实测 Valkey 9.0.4 在压测中 CPU 峰值 45%、内存 16%。
3. **协议与客户端完全兼容**：RESP 协议、命令语义、Lettuce 客户端全部无需改动，  
   切换只是改一个 host/port。

配置示例（`application.yml`）：

```yaml
jmqtt:
  broker:
    redis:
      enabled: true
      host: 127.0.0.1        # 换成 Valkey 地址即可
      port: 6379
      mode: standalone       # standalone / sentinel / cluster 三种都支持
```

部署建议：

- **关闭 RDB / AOF**。这里存的是会话元数据与在途镜像，不是业务数据；  
  broker 侧已有 `write-back` 与过期回收，落盘只会带来 fsync 抖动。  
  `valkey.conf` 里 `save ""` + `appendonly no`。
- **`maxmemory-policy` 用 `noeviction`**。会话被静默驱逐会导致客户端重连后  
  收不到离线消息，且不会有任何报错——宁可让写入失败暴露出来。
- **别把它当缓存用**。如果同时还要拿它做业务缓存，请分实例，不要和 broker 共用。

## 设计

每条 PUBLISH 从收包、路由到写给订阅者，只接触进程内存。Redis 只出现在低频路径  
（连接、重连、接管、订阅变更），且都是 write-back 镜像；Kafka 只在集群总线与  
上行数据面上，同样不在路由路径上。收益有两层：外部往返不进单条消息的延迟，  
外部故障也不拖垮本地投递。

### 路由

订阅关系放在内存前缀树里，匹配 `a/b/c` 就是沿树走三层，与订阅总数无关——  
连接从 1 万涨到 40 万，匹配步数不变。读路径无锁（弱一致迭代，新订阅最多晚一次  
投递生效），写路径单把锁只串行化本节点的订阅变更。

### 集群

节点完全对称、没有 leader，也没有「先协调再投递」的环节：

- 跨节点 pub/sub 走 Kafka，消费端先拿主题对本地订阅树匹配一次，  
  没有本地订阅者的消息在反序列化之前就丢弃；
- 会话归属是一次 Redis 原子操作（读出旧 owner、写入本节点），  
  归属转移时定向通知旧节点释放连接，而不是仲裁或投票。

设计细节见 [docs/cluster-broadcast-rationale.md](docs/cluster-broadcast-rationale.md)。

## 能力清单

- **接入与路由** —— 内存前缀树、QoS 0/1/2、保留消息、遗嘱消息、连接接管、  
  WebSocket、TCP 与 WS 可分别关闭
- **持久会话** —— write-back 到 Redis/Valkey，会话属性与订阅关系一并存，  
  重连到任意节点都能完整恢复
- **离线消息队列** —— 持久会话的客户端离线期间 QoS 1/2 入队（有界，超出丢最旧），  
  重连后按序投递
- **发送窗口与背压** —— 未确认 QoS 1/2 不超过 `max-inflight`，每连接有界发送队列，  
  QoS 0 受写缓冲保护
- **在途消息持久化** —— 已发未确认的 QoS 1/2 落镜像，节点崩溃或跨节点接管后  
  以 `dup=1` 重发且报文标识符不变
- **接收方向 QoS 2 去重** —— 拿到 PUBREC 前带 `dup=1` 重发是合法的，服务端只投递一次
- **集群** —— Kafka 总线、跨节点连接接管通知、广播范围三态可配  
  （全部 / 按过滤器 / 不广播）
- **管理面** —— 节点概要、客户端注册表、订阅视图发布到 Redis；  
  控制台只读 Redis，不直连 broker。另有命令通道做驱逐/踢下线
- **可观测** —— `/actuator/prometheus`，指标覆盖连接、投递、丢弃、背压、集群总线

## 已知边界

这个分支为了场景匹配做了取舍，以下是需要提前知道的：

1. **v5 客户端连不上** —— 收到「协议版本不支持」。若存在发 v5 CONNECT 的固件版本，  
   需先确认。
2. **v5 的拒绝没有 CONNACK** —— Netty 解码层对 v5 报文结构不匹配时抛的异常不在  
   `handleDecodeFailure` 的识别范围内，表现为连接被直接关闭。排查时容易误判成网络问题。
3. **ACL 拒绝的 QoS 1/2 不回确认** —— 客户端会超时重发直到 ACL 变更或断开。  
   这是 3.1.1 没有逐条错误通道的固有限制。
4. **SUBACK 失败码只有 0x80** —— 无法区分「过滤器非法」与「未授权」。
5. **UNSUBACK 不带逐项结果** —— 逐项成败只进日志。
6. **广播关闭时跨节点订阅静默收不到** —— `broadcast-enabled: false` 的前提是  
   「集群内不存在跨节点 MQTT 订阅」。若判断错了，症状是消息不报错地丢失。
7. **无配额体系** —— 没有全局/单 IP 最大连接数、单客户端发布速率限制、  
   单客户端订阅数上限。需要靠前置 LB 与设备侧约束。
8. **Spring Boot 2.7.18 已 EOL** —— 基线无安全补丁，对公网暴露需评估。

## 与 main 分支的差异

`main` 保留 3.1.1 + 5.0 双栈，本分支只保留 3.1.1（兼容 3.1）。

| 项                | main                                                              | v3-lite                                 |
| ---------------- | ----------------------------------------------------------------- | --------------------------------------- |
| 协议               | 3.1.1 + 5.0 双栈                                                    | 3.1.1，兼容 3.1；v5 握手阶段拒绝                  |
| `ReplyFactory`   | 324 行，9 处版本分支                                                     | **191 行，无版本分支**                         |
| `ConnectOptions` | 8 个字段（含 SEI / Receive Maximum / Packet Size / Alias / Will Delay） | **2 个字段**（cleanSession / sessionExpiry） |
| 出站回包             | 按连接版本构造两套形态                                                       | 只有一种形态                                  |
| 订阅处理             | 含 Retain Handling 与 v5 细分失败码                                      | 只有 0x80 一个失败码                           |
| ACL 拒绝           | v5 回 0x87 原因码                                                     | 只有静默丢弃                                  |

其余能力（QoS 0/1/2、保留消息、遗嘱、连接接管、持久会话、离线队列、发送窗口与背压、  
在途持久化、Kafka 集群总线、Redis 会话持久化、管理面）两个分支一致。
